# TheApp - Capability Checklist

- [x] **Phase 1 — Foundation**
  - [x] TheApp installs on a clean machine - Installability treated as a 0.1.0 feature rather than a packaging afterthought, so no source-mode path ever diverges from the installed one. Per-user install, no elevation, unsigned with a published SHA-256, and one self-contained file with no runtime prerequisite. Not statically linked in the C sense - native libraries self-extract on first run - because architecture.md §9 shows that phrase has no clean referent in .NET, and NativeAOT stays deferred until the native dependency set is stable.
  - [x] TheApp keeps your key and your state safe - Settings survive a restart, unknown keys are rejected, and everything writable lives in one folder beside the executable. Two stores because one loader cannot both fail loudly and shrug; writes go to a `.writing` sibling then an atomic move, and secrets are DPAPI-encrypted at rest.
  - [x] TheApp says what went wrong - Levels, one target per subsystem, structured fields, and two sinks - one human-readable, one machine-readable so an agent can parse a session. No telemetry leaves the machine: no analytics, no metrics endpoint, no upload. Provider traffic is a separate claim with a separate row, because INARA, a cloud LLM, a paid TTS and web search all send journal-derived content off the machine when enabled.
  - [x] Turn a subsystem up without restarting - Runtime per-subsystem verbosity control.
  - [x] TheApp calls a capability - A request produces a real tool call that runs and returns a result, covering the capability registry and the descriptor declaring identity, tools, help, settings rows and display model. Descriptors are registered once and never mutated, and every tool profile's schema block is byte-identical across turns, so prompt caching survives a mode change.
  - [x] Every capability has a documentation page - CI fails if a registered capability has no documentation page, making "write the docs later" impossible rather than merely discouraged. Pages are written from real artifacts and must quote at least one code block or line of real output.
  - [x] GitHub Pages documentation - Each capability should have a documentation page. General help for TheApp outside of the particular capabilities is also available.

- [x] **Phase 2 — Journal spine**
  - [x] Journal behavior is testable without the game - A recorded session replays deterministically at 1x and 100x with no game, headset or hardware. Fixtures are byte-preserved via `.gitattributes` and scrubbed of the Commander name and real system visits, since the repository is public.
  - [x] TheApp knows where you are - TheApp answers what system you are in from the journal as part of an ordinary turn. Picks the newest journal by ordinal filename sort, opens shared for read/write/delete since Elite holds the file open, and is pull-based with no internal thread, which is what makes it testable.
  - [x] Survive a journal schema change - Elite adds and changes journal events several times a year. Unknown events are logged and skipped, a parse failure never kills the tail loop, and the machine-readable sink makes the diff findable, so a game patch costs a morning rather than an outage.
  - [x] Handle more than one Commander on a machine - A second Commander's journals must not merge into the first one's fleet, materials or location. The Commander is identified from the journal header and all derived state is kept per Commander, because a naive newest-file reader silently blends two people into one.

- [x] **Phase 3 — First conversation (typed)**
  - [x] TheApp answers a typed question - Type a question into TheApp's window and get a streamed reply from the model.
  - [x] Ship's AI Unsure - An explicit "unsure" result instead of a confidence threshold, because models produce confident-sounding scores that do not mean anything. A model-free keyword router ships alongside so the whole path is exercisable without a model.
  - [x] Capabilities as state, not guard - For example, an LLM or TTS experiencing downtime or token depletion flips a capability off and the next turn reads what is currently available, so there is no failure handler to author or keep in register. It falls out that every input path must be answerable with no capabilities at all.
  - [x] Model Level and Thinking - LLM attempts to gauge per-turn thinking effort from low through max, but no "off" unless the LLM is set to "none" or through transient degradation.
  - [x] LLM Turn Price - Per-turn token usage including cache reads, priced from a table, plus a running total. A profile switch is the only sanctioned cause of a cold prefix, so an unexplained cache miss is a regression the running total can surface rather than hide.

- [x] **Phase 4 — Settings surface**
  - [x] TheApp is configured without manually editing a file - Every setting, including the voice, is changeable in the UI with no hand-editing. Rows are generated from capability descriptors, defaults appear as placeholders rather than values, keys are write-only, and safety-critical rows are protected from the model.
  - [x] Apply every setting without a restart - Changing a setting takes effect immediately (no need to manually "save").
  - [x] Offer one searchable picker everywhere a value is chosen - A command-palette style picker with keyboard navigation, reused for voices, models and devices. Fail-soft by contract: with an empty list you can still keep the current value or type one.
  - [x] Show the controls the active provider actually has - Settings adapt to the selected provider instead of showing a hardwired set, and changing an endpoint resets the model list to that endpoint's namespace rather than leaving a stale selection.
  - [x] Settings only expose specifics of a provider (LLM, TTS, STT), such as selected voice(s), Model, etc. for the currently selected provider.
  - [x] Protect safety-critical settings from the model - Rows gating keyboard actions and macros are marked protected: never changeable through a tool the model can call, because the model consumes untrusted text and a guard it can flip is privilege escalation. Protected is a property of the caller, not of the modality. The panel, a hotkey and the model-free keyword router all reach these rows; the LLM path does not.
  - [x] Say what each provider receives - A settings row and a documentation page stating exactly what leaves the machine for each enabled provider: system and station names to INARA, turn text and game context to a cloud LLM, reply text to a paid TTS, query text to web search. What is currently leaving is answerable at any time, and every destination can be turned off. Amended in Phase 12: this used to promise local-only operation as a named configuration, which priced every later feature against a slogan rather than against the enumeration - what is owed is that nothing reaches a network without appearing in the list.
  - [x] Link each settings row to its documentation - A setup-guide link per settings row pointing at that setting's page. In-app help stays the short form; the page is the long form.
  - [x] Collapse settings cards - Collapsible sections whose collapse state is remembered as a view preference, not a setting, and applied before first paint so a collapsed card never flashes open.
  - [x] Settings Nav Menu - Is present and highlights the section based on the topmost visible setting.
  - [x] Hotkey Binding - (Only in main window) Press the key to bind it.
  - [x] Themes - Dark, light, default Elite-flavored, Guardian, and based on the current Elite Color Scheme palette, with color living in one place so no view hardcodes a literal.

- [x] **Phase 5 — Speaking**
  - [x] One audio stream - Everything audible goes through one queue with priority and supersede, including audio cues, so ducking, interruption and captioning need no second mechanism. One arbiter for every voice, because separate paths per voice are how a line gets spoken in the wrong one. The arbiter exposes a render-side reference tap from the start, since echo cancellation needs the far-end signal and retrofitting that tap means opening the one component every voice path depends on.
  - [x] TheApp speaks its answer aloud - The reply is audible in the chosen voice. Synthesis is sentence-chunked so speaking starts at the first sentence boundary - the largest perceived-latency win available.
  - [x] Say so when the model is misconfigured - An audible warning when the provider setup is wrong, rather than silence that is indistinguishable from a model with nothing to say.
  - [x] Say something when a turn is taking too long - Retry with backoff (N tries, X wait, sequential or logarithmic), and if exceeded say so aloud in the current voice rather than leaving silence.
  - [x] #20 Give every loop state its own audio cue - One default per state. Cue names come from the shipped resources rather than a hand-written table, since a wrong name goes wrong as silence nobody notices.
  - [x] #18 Play a thinking bed while the model works - Audible evidence that TheApp heard you and is working, instead of dead air while a turn runs.
  - [x] Stop - An always-available instant silence that supersedes everything on the queue and stops mid-sentence, reachable by voice and by hotkey and never gated behind a turn completing. A companion that talks is only tolerable if it can be silenced faster than it can finish a sentence.

- [x] **Phase 6 — Listening**
  - [x] Choose the microphone in settings - Pick the input device instead of inheriting the system default. A blank selection produces a silent default and a turn reporting no speech detected, with nothing indicating why.
  - [x] PTT - Hold the key, speak, release, and your words appear. The key-down path awaits nothing before recording starts, and push-to-talk is one gate policy over an audio stream so continuous listening and wake word become later policies rather than a rewrite. May be set as a "toggle" rather than true PTT via settings.
  - [x] STT Model Choice - Commander can choose which Whisper model to use and whether or not to allow it to run on the GPU. In VR the GPU is already the scarce resource, so a large model running there surfaces as dropped frames and reprojection rather than as anything that looks like a speech problem, which is the hardest kind of setting to diagnose. GPU is opt-in with that cost stated on the row, and the default is CPU whenever a headset is present - a short push-to-talk clip on the small English models absorbs that fine.
  - [x] Bias transcription with proper nouns from the journal - Feed system, station and ship names from the journal into the transcriber so they come back spelled correctly. Journal-derived and network-free; proper nouns are where speech recognition fails hardest and most silently.
  - [x] Report a key that is bound twice - A double-bound push-to-talk key currently has no symptom other than not working; detect the collision and say so. Reads the same parsed binds as keyboard-action reachability rather than keeping a second view of the Commander's controls.
  - [x] Settings by voice - Unless otherwise noted, every setting should be settable by voice. Protected rows are reachable by voice only through the model-free keyword router, so "by voice" never silently means "by the LLM."
  - [x] Answer what can you do, from the registry - Spoken help projected from the capability registry - groups, then capabilities, then detail and example phrasings - ranked by real usage. The model is never asked what TheApp can do, because asking produces confidently invented capabilities.

- [x] **Phase 7 — Knowing the game**
  - [x] Know what is happening around you - Live situational awareness attached to each turn: where you are, what you are flying, and what just happened.
  - [x] Know your location and your carrier (if owned) - Current system, station and body, plus where your fleet carrier is.
  - [x] Ship's loadout - Modules and stats from the loadout event.
  - [x] Ship metrics - Base jump range and similar, computed from what the loadout event actually reports rather than from a table of ship specifications.
  - [x] Know what ships you own and where they are - A fleet registry built from stored-ships journal events.
  - [x] Know what materials you are carrying - Materials inventory built from journal events, answerable without an external lookup.
  - [x] Know what is in your backpack and ship locker - On-foot inventory parsed from the local files Elite writes.
  - [x] Session summary - Earnings, bounties, exploration data sold, materials gained and jumps made since the session began, built from the journal already being tailed rather than from anything new.

- [x] **Phase 8 — Proactive speech**
  - [x] Call out danger without waiting for a turn - Interdiction, shields down, hull damage, dangerous heat and a full cargo hold announce themselves from journal and Status.json events. These fire on the event and never at the model's discretion, because an alert that depends on a turn completing is not an alert.
  - [x] Fuel and range safety - Low-fuel warning against the current tank, plus the case that actually strands a Commander: the next star on the route is unscoopable and the one after it is out of range. The journal and the route file supply both, and the warning is unconditional rather than something the model may decide is not worth mentioning.
  - [x] Route Progress - Jumps remaining (every N systems (setting)), next system, neutron and white-dwarf hazards ahead, and scoopable-star ambiguity resolved rather than guessed. Reads the route file Elite writes locally, so no route-planning service is needed.
  - [x] Remark on an unusually long jump - Flavor during a longer-than-normal hyperspace jump, fired once hyperspace has actually been entered rather than on the jump being initiated. Threshold is configurable but defaults to 30 seconds.
  - [x] Recognize where you have arrived - Place-aware callouts for engineer bases, notable stations.
  - [x] Home System - Home callout when you arrive in your home system (setting).
  - [x] Call out material-gathering milestones - The first unit, then 25/50/75%, a running count above 75%, and full. The tracker is primed from the session backlog at startup; otherwise starting TheApp after Elite means the milestones never fire.

- [x] **Phase 9 — VR**
  - [x] Order agnostic Overlay - The order of starting SteamVR, Elite Dangerous, TheApp, doesn't matter.
  - [x] TheApp appears in the headset - Captions render over Elite in VR through OpenVR (Elite never calls OpenXR) and clear on their own. Captions are their own unmovable, output-only, ephemeral layer with a rolling three-line window timed from the end of speech. Captions follow Netflix CC standard.
  - [x] Configure the captions - Follows Netflix CC standards.
  - [x] TheApp's panel works in VR - One widget tree renders to both the desktop window and VR, so the windowed UI can never be more functional than the headset one. Mini is a mode of the same panel - a reduced content set - not a separate surface or a scaled-down copy.
  - [x] VR Panel locking - Head-locked or world-locked placement, per surface. Choosing world-locked implies re-anchor is bound and reachable off-panel.
  - [x] Re-anchor the panels - Elite's in-game recenter moves the cockpit without telling SteamVR, so world-locked surfaces drift out of position with no event to hook. A Commander-triggered re-anchor snaps every world-locked surface back to current head pose and preserves their relative layout rather than stacking them. Reachable by voice and by hotkey, never only from the panel, because a drifted panel is precisely the case where you cannot aim at it. Head-locked surfaces and the caption layer are unaffected.
  - [x] Overlay Positioning & Look - Opacity, curvature, distance, size, and scale, configurable per surface.
  - [x] Panels can switch between curved and flat - The panel is bent {curve setting} around the Commander.
  - [x] Open at a size that fits the screen - Avalonia already matches the monitor's scaling: Width and Height are device-independent pixels, so the 820x640 default is 1230x960 actual pixels at 150%. That is the problem rather than the fix - it is nearly the whole usable height of a 1080p display and taller than a 1366x768 laptop screen outright, because the default was chosen at 100% and never checked against a scaled work area. The opening size is clamped to the working area of the screen it actually appears on, and the size and position the Commander leaves it at are remembered like the panel's collapse state already is, so the default only ever has to be right once.
  - [x] Zoom the desktop window - Ctrl and the scroll wheel, Ctrl+plus, Ctrl+minus, and Ctrl+0 for 100%, because every browser has already taught the Commander those four gestures and a panel that invents its own is a panel they have to be told about. Scales the rendered panel rather than restyling its text, so layout and spacing survive at any level, and it applies to the settings window too since that is the same widget tree. The level persists between sessions like the theme does. This is a desktop item living in a VR phase: its natural home was Phase 4 and that phase is closed, and it belongs beside *Scale the big panel* anyway - shipping a zoom for the headset and none for the window makes the windowed surface the lesser of the two, which is the same parity the one-widget-tree item is protecting from the other direction.
  - [x] Scale the big panel - Zoom the panel up and down in the headset, distinct from mini mode, which reduces content rather than shrinking the rendering.
  - [x] Keep working when the main window is minimized - In 2D or in VR, if TheApp is minimized, all 2D, VR, and voice functionality still works.

- [x] **Phase 10 — Acting on the game**
  - [x] Know which actions the Commander can actually reach - Parse the binds file and know which in-game actions have a keyboard binding at all, because the audience is HOTAS-heavy and a stick-only action asked for by voice fails as silence. Unbound actions are excluded from the advertised profile and asking for one gets a spoken reason instead of nothing. Read-only: TheApp never writes the Commander's bindings.
  - [x] Autonomous actions are opt-in per action - Every other capability acts on something the Commander said. An action that fires a game input on a journal event with nobody asking is a different category and needs its own consent, so each one is off by default and enabled individually. The category gets its rule before the second member of it exists.
  - [x] TheApp honks (discovery scanner) when you arrive in a system - The discovery scanner fires on entering a system using the Commander's own key binding, injected via scancodes with the Elite window focused. Never installs a low-level keyboard hook, and `release_all()` is unconditional because a stranded key here is a throttle that will not stop. The first member of the autonomous-action category and therefore off by default and enabled on its own row.
  - [x] Offer only the actions that work right now - Mode-gated action advertisement, so the set differs on foot, in the SRV, in supercruise and in normal space. The cockpit is not one mode: hardpoints, cargo scoop and landing gear do nothing in supercruise, and Status.json flags supply the split for free. The model is never told about a key that currently does nothing, whether the reason is the mode or the absence of a binding.
  - [x] Decide which tools ship on a turn as the count grows - At some capability count the tool schemas stop fitting comfortably in context and something must choose between them. The choice is between pre-declared profiles, not between individual tools, so budget pressure degrades to a smaller profile instead of destroying caching on the exact turn caching starts to matter. Whatever is chosen, the anti-invention guardrails are static prompt material and must never be strippable by a budget or effort setting.
  - [x] Control flight and navigation by voice - Landing gear, lights, cargo scoop, hardpoints and the frame shift drive.
  - [x] Control ship systems by voice - Power distribution, fuel scoop, silent running and heat sinks.
  - [x] Control panels, UI, and fire groups by voice - Cycle the panels and fire groups without taking a hand off the stick.
  - [x] Control the SRV by voice - Toggles only (turret, forward/back, dismiss/recall ship, board, exit SRV, etc.).
  - [x] Put something on the clipboard - A system name, route or value placed on the clipboard so it can be pasted into the game or a browser.
  - [x] Galaxy Map - Set a course by sending keystrokes to the in-game galaxy map. Best-effort rather than guaranteed, since it depends on map focus, layout and the game's language setting, so the clipboard route is the primary path and auto-plot is the convenience layered on top of it. A failed plot says so rather than leaving the Commander believing a course is set.
  - [x] Send/Receive messages to another commander or commanders - Dictate into Elite's chat: local, wing, system.
  - [x] Macros - Named multi-step voice-triggered sequences, validated against closed vocabularies and the action allowlist. Invocation is by voice; authoring is not, because composing a new action sequence is the one input whose vocabulary cannot be closed in advance. This is the exception to "every setting can be set by voice."

- [x] **Phase 11 — Persona and voices**
  - [x] Personas - Pre-built companion characters the Commander can choose between. Guardian Flavored.
  - [x] Ship AI Naming - Defaults to Persona's name, but may be set by the commander.
  - [x] Say when the persona has changed - New persona acknowledges when it has been picked. If it changes before its acknowledgement has completed speaking, it stops and the next one starts. Speech, as always, may be interrupted by the commander.
  - [x] Personality on/off - Plain answers with no persona, flavor, or ambient remarks. The anti-invention guardrails must survive the persona being switched off, so they cannot live inside the persona's prompt block.
  - [x] Commander's About Me - A Commander-provided prompt stored between sessions and personas so that the LLM remembers basic facts about the commander.
  - [x] Ship's AI Avatar - Per-state avatar imagery on the panel. Animated formats supported.
  - [x] ElevenLabs - First offered, paid voice provider alongside the free Edge Neural voices, chosen per role, so a Commander with a key hears it and nothing else changes. Other providers may be added later in development. Differences between providers, such as speed, is maintained on a per-provider basis.
  - [x] #33 Pair a default voice to each persona - At first startup, lazy-load available voices (Edge neural defaults to "en-" voices). Using LLM (if available), a sensible voice is chosen for each persona based on the persona's prompt (or custom prompt) in the background, so picking a character does not also mean auditioning potentially hundreds of voices.
  - [x] Ambient Voice - In-character ambient lines motivated by live game state, varied (by LLM if available, otherwise by initially the 10 generated stock phrases per game state covered).
  - [x] Speak incoming messages in another voice - Re-voice in-game communications so they do not arrive in the ship AI's own voice.
  - [x] Voices "stick" - Once a voice has been chosen for a sender it stays with them. NPC identities are scoped to the system, since the cast turns over on a jump. Player Commanders are scoped to the session and survive hyperspace, because a wingmate whose voice changes on every jump reads as a bug rather than as variety.
  - [x] Carrier Captain - If a player owns a Fleet Carrier, they can choose dedicated voices for the Captain and Tower Control, with varied LLM arrival and departure responses.
  - [x] Ship Crew - Multi-character roleplay with invisible crew (aside from the Ship's AI) on the conversation path, with per-ship rosters drawn from the real fleet and hired NPC pilots imported from the journal with their roles. Crew is addressable and responsive via LLM.

- [ ] **Phase 12 — Soundscape**
  - [x] Three pages for the transcript - The big text area is one of three pages, chosen by tabs along the top of it: **Conversation** (the Commander and the ship's AI, and nothing else), **Technical** (the same with the diagnostics left in, which is what the panel always showed), and **Log file** (today's log, read when the page is opened). The split rests on the caller naming the kind of line as it writes it, because it is not recoverable afterwards - a version banner and a reply are both text, and separating them by pattern is guessing at somebody's prose. The page is a property of the surface like `PanelMode` is, and for the same reason: both surfaces bind one model, so a page held there would send the headset to the log the moment the window went to it. Mini shows no tabs, being the tail and the provenance line and nothing else. They have to read as tabs rather than as buttons or links, which is a property of the join and not of the label: the selected one shares the panel's fill and drops the border where they meet. Verify by looking at the captures.
  - [x] One type scale, and d47's own text sized to match its controls - A row's label reads smaller than the value it labels: every control renders at the framework default of 14 while d47 sets its own text by hand at 10 to 13, so a label is 13, its help is 11, and the combo box beside them is 14. The fix is to raise ours rather than shrink the controls - a settings surface is read at a glance from a metre away in a headset, and the answer to that is never less type. Forty-six size literals across seven files with nothing naming them is why they drifted apart in the first place, so this replaces them with a scale named by role - heading, subheading, body, secondary, small - and body is whatever the controls are. Touches `PanelView` as well as the settings surface, since the avatar landed there in Phase 11, and both surfaces have to move together or the headset and the window disagree about what a label looks like. Verify by looking at the render captures across themes at more than one zoom level: the failure this is fixing was visible in a screenshot and invisible to every test.
  - [ ] **Settings is a tab of the main window, not a second window** - One visible window. Settings becomes another tab in the strip that already carries Conversation, Technical and Log file, and takes the place of the big multiline text area when it is selected; the Ask line below it gives way to the settings footer, which is where the storage line and its own controls already live. The short-lived modals stay modal - About, confirm, the picker, hotkey capture. The plumbing is nearly free: `SettingsView` is a window-agnostic `UserControl`, every dialog it opens takes its owner from `TopLevel.GetTopLevel(this)` and re-parents, and the second `ZoomHost` and window-placement slot both retire. The real work is width: the settings surface is a 224px nav column plus a 700px minimum and opens at 1180, against a panel window of 820 meant to sit beside a running game - so the nav column has to collapse below about 900, or the second window has not been removed so much as the first one made too big to keep on screen. Two behaviours need deciding rather than porting: what Escape does when there is nothing to close, and hotkey capture now tunnelling on the same top level that carries the open-settings and focus-ask gestures. The VR overlay renders the panel and must not gain a settings surface it was never sized for - mini already hides the tab strip, and full has to keep the tab out of the headset rather than showing a 1180px column at a metre.
  - [ ] Search whichever tab you are looking at - One search affordance for the main window, on the tab that is selected: Conversation, Technical, Log file, and Settings once it is a tab rather than a window. One control and one gesture, not four features bolted to four pages - Ctrl+F focuses it, Escape clears it and gives the page back. What a match *does* differs by page and that difference is the design rather than an inconsistency: the transcript pages are prose, so a query highlights every hit, says how many there are and steps through them, leaving the surrounding lines in place because reading back a conversation means reading what was around it; Settings is 92 rows across 14 sections, so a query **filters** - rows whose label, help text or key match - and the nav column shows only the sections still holding something, since highlighting in place in a haystack is a scroll hunt with extra colour. The query belongs to the page and is dropped when the page changes, because one string that filters here and highlights there is a control that behaves differently depending on where you last clicked. Must not fight the log arriving underneath it - a hit found in the live log stays found as lines append, which is the same problem *Follow the live log* solves and should use whatever answer that reaches. Desktop only: the headset has no keyboard, mini shows no tab strip, and a search box the Commander cannot type into is worse than no search at all.
  - [ ] Anything that might take a moment says it is working - The rule already written into the picker button - "a button that looks unchanged for a second reads as a button that did not take the click" - applied everywhere it is true rather than at the one place it was noticed. Opening the Log file tab reads a file off disk; a model list, a voice list and a key verification each cross the network; a gap reaction spends a model round trip before the core says its first word. Each of those can look exactly like nothing happening. **The affordance that was touched is the thing that shows it** - the tab, the button, the row - never a spinner somewhere else on the surface, because a Commander who clicked here does not look there. Reuse `BusyGlyph`, which exists for this. Two failure modes to hold off at once: no silence on the slow case, and **no flash on the fast one** - an operation that finishes in 40ms must not strobe, which means a short delay before showing and a minimum time on screen once shown, and those two numbers stated in one place rather than chosen per call site. The control shuts while it works, as the picker's already does, so a second click cannot queue a second copy of the same fetch. Written as something a call site opts into in one line, not as a pattern to be reimplemented: the next long operation is the one that will ship without it. Verify from the captures - both surfaces, because the headset shows the same widget tree and a glyph that only animates on the desktop is half an answer.
  - [ ] #96 Ambient audio mixer - Per-category levels and mute, plus how each category ducks against speech.
  - [ ] Custom Sound Cues - Drop in your own audio files and have TheApp use them, kept distinct from the set TheApp ships with.
  - [ ] Ambient music - Music separate from cues and sound effects, with its own level and its own ducking behavior against speech. Ambience is situational based on journal or "general."
  - [ ] Pick up dropped-in audio without a restart - Cues, sound effects, music and ambient content discovered from convention folders and reloaded live.

- [ ] **Phase 13 — Hands-free listening**
  - [ ] Echo Cancellation - Acoustic echo cancellation, for continuous listening and natural interruption. Consumes the render reference tap from the single audio arbiter rather than a loopback capture, which is both lower latency and correctly aligned. WebRTC AEC3 is BSD-3.
  - [ ] Voice Activity Detection (VAD) - (An option) Voice activity detection as a continuous-listening gate policy over the existing stream.
  - [ ] Wake Word - Wake-word gating, implemented as another gate policy over the same audio stream.
  - [ ] Show that the microphone is open - Once wake word or VAD means continuous capture, listening state is visible on both the panel and the VR surface. Continuous capture with no visible state is the thing a user is right to distrust, and the indicator is a property of the gate policy rather than of any one capability.

- [ ] **Phase 14 — Knowledge and external data**
  - [ ] Galaxy Search - Systems, stations and bodies, distances computed from coordinates. Query parameters are validated locally because the search service ignores filter keys it does not recognize.
  - [ ] Find Nearest - Nearest module, nearest ship for sale, stored ships and modules, plus body and signal lookups.
  - [ ] Route Planning - Neutron and long-range plotting, trade loops, Road to Riches, and mining routes.
  - [ ] Elite Dangerous Ships - Ship and module specifications from a dataset lazy-queried at runtime and generated when new ships are detected.
  - [ ] Engineers - Who unlocks what (and who in the chain of unlocks), current unlock status, where each engineer is, and what they grade.
  - [ ] #102 Help with engineering - Blueprints, material sourcing, per-ship engineering plans, and on-foot suit and weapon engineering. At least two epics' worth, deliberately left vague until it is next.
  - [ ] Know the current community goals - Active community goals and their tiers. CGs the commander is not currently participating in can only be surfaced if an INARA API Key is available and correct.
  - [ ] Web Search - Live web search as a tool, when determined necessary by the LLM or when specifically asked to by the commander.

- [ ] **Phase 15 — Activity assistants**
  - [ ] Exobiology sampling - Genus, the required sample spacing for that genus, whether the Commander has moved far enough for the next sample, and what has already been scanned on this body. The spacing rule is the whole feature: it is the number nobody can eyeball and the reason a sample gets wasted.
  - [ ] Colonisation and construction tracking - Commodity requirements and delivered-so-far for an active construction site, sourced from the journal. This is where a large part of the current playerbase spends its hours, and the running arithmetic is exactly what a Commander should not be keeping on paper.
  - [ ] Prospector and core callouts - Material percentages from prospector limpet results and core asteroid detection, spoken in the ring where mining actually happens. Route planning gets the Commander to the ring; this is the part that happens after they arrive.
  - [ ] Warn about an attack that has been announced but not yet landed - NPC comms carry the intent before the shooting starts, as localisation ids rather than prose, so this is an allowlist of ids and never a keyword match on text. Measured over 912 real journals: `$Pirate_StartInterdiction*` precedes an attack 88% of the time, `$Pirate_OnDeclarePiracyAttack*` 66%, `$BountyHunter_StartInterdiction*` 1 for 1, with a median of 10 seconds' warning and 315 of 406 inside 30 seconds - enough to boost, deploy hardpoints or high-wake. The allowlist is what makes it work: `$Trader_OnEnemyShipDetection*` fires 2,399 times at 1%, and `$HostileScan*` 48 times at 0%, so anything matching on "sounds hostile" cries wolf a hundred times per real event. Each id group gets its own spoken line and its own alert cue rather than one generic warning, because the game has already told us which situation it is. In-game comms are untrusted input, so the match is a local comparison against a fixed set and the message text never reaches the model.
  - [ ] Warn that you are exposed in a rival Power's territory - In normal space, in a system whose `ControllingPower` is not the Power you are pledged to. A standing condition rather than an event: it announces on entering the condition and is silent while it holds. Deliberately not on arrival, because arriving is a supercruise state and nothing can reach you there - measured at 0% across every Power security contact in supercruise, against 67% in normal space. Suppressed while an attack is already in play: "be careful, you are in enemy territory" arriving as a Thargoid or a pirate opens fire is worse than silence, so anything on the danger path outranks it. The Commander's pledge is tracked as history from the `Powerplay` event rather than read once, because it changes. **What this cannot be:** the thing actually wanted here is a warning when a Power Security ship appears in the contacts panel, and no third-party app can see that - across 221 event types Elite has ever written there is no contact, spawn or proximity event, no state file holds a contacts list, and every signal about another ship (`ShipTargeted`, `ReceiveText`, `Scanned`, `UnderAttack`) requires it to have already acted. `$PowersSecurity_OnAttackStart*` is real and names the Power, but arrives 0-4 seconds before the shot, so it is confirmation rather than warning. This item is the reachable half and should say what it knows - that you are exposed - rather than implying something is near.

  - [ ] TheApp keeps "The Ultimate" checklist - CRUD + complete/uncomplete and read checklist items by voice, with the panel reflecting changes live.
  - [ ] Per ship build planning/tracking - Checklists that belong to a specific ship and follow it, instead of the universal checklist.
  - [ ] LLM Ship AI may propose that a checklist item is done - Where the journal can tell, TheApp asks whether a checklist item is complete and marks it only after the Commander agrees.

- [ ] **Phase 17 — Session tooling and release polish**
  - [ ] Remember which voice you chose for each provider - Voice choices are dropped when the speech provider changes, because a voice id means nothing to a provider that did not issue it, so switching to ElevenLabs and back re-picks eleven cores from scratch and forgets the ship's own voice twice. `SpeechSettings.ProviderRates` already keeps the speaking rate per provider and is the shape to copy; voices are a larger structure - the ship's, two named roles and one per core - which is why the fix that stopped the silence dropped them rather than waiting on a schema that can hold all of it twice.
  - [ ] Hear a voice before you choose it - The voice picker lists several hundred names and a Commander is picking a character's voice from them, which is a judgement no label supports: "Bill - Wise, Mature, Balanced" and "George - Warm, Captivating Storyteller" are both true and neither tells you which one is Warden. Audition from the dialog: the highlighted voice speaks a line, without closing the dialog and without committing the choice, so the Commander can walk the list and listen. **The line is the core's own** - its intro, or the first sentence of it - because a voice is being cast for a character and a generic sample is a different question than the one being asked. Through the one arbiter like everything else that makes a sound (architecture.md D7): an audition ducks and is cut off by the shut-up hotkey exactly as speech is, and starting a second audition drops the first mid-word rather than queueing behind it. **Auditioning a paid voice costs money** — each press is a synthesis request billed by the character — so it is a press rather than a hover or a selection-changed, it is never automatic, and it is counted by whatever *What the voices cost* lands as. Cache the clip for the session, since walking back and forth over four candidates should not be four purchases each way. Free where the provider is free, unavailable with no provider at all, and the button says which of those it is rather than being silently inert.
  - [ ] Spike: what voices does a *new* ElevenLabs account actually offer - `ElevenLabsTtsProvider` lists `GET /v1/voices` and treats the result as "what the provider offers". Nobody has checked what that returns for an account created five minutes ago. If it is My Voices only, a new Commander's picker is **empty** on the provider they just paid for, the per-core pairing has nothing to pair from, and the named default that gives Warden "George" silently does not apply — three failures that all look like "d47 is broken" and none of which the current code can tell apart from an unreachable API. Answer four things: what the endpoint returns on a fresh account; whether the premade voices (George, Matilda, Callum and the rest) are in it or only in the shared library behind a separate endpoint; whether a shared-library voice can be spoken directly by id or has to be added to the account first; and whether adding one is a call d47 could make, or a thing the Commander must do on the website. The answer decides whether the picker needs a second source, whether the named default needs to survive the voice not being listed, and what the empty-list case should actually say. Throwaway probe under `spike/`, finding written to `docs/spikes/`, per `spike/README.md`.
  - [ ] What the voices cost, beside what the model costs - A running total for paid speech, kept for the session and shown next to the LLM turn price so "what has this cost" has one answer rather than one per subsystem. The unit is **characters, not tokens**: ElevenLabs bills per character, Edge bills nothing, and reusing the token shape would quote a number whose basis is wrong. Counted at the `ITtsProvider` seam, where the text is actually handed over, because that is the only place every caller passes - the ship's AI, a callout, a re-voiced in-game sender and a core's own introduction all converge there, and counting at any caller means missing the next one. Counted on the synthesis that **succeeded**: a refused voice or a failed request costs nothing, and a turn cut off by the shut-up hotkey has already paid for the sentences that were synthesised before it - which is the case that makes "count what was sent" different from "count what was said", and the one worth a test. **Characters are a fact and dollars are an assumption**, and the row has to keep them apart: ElevenLabs' per-character price is a property of a subscription tier that the API does not report, so the character count is always shown and a dollar figure only where the rate is known - stated on the row and editable, defaulted rather than invented, in the same spirit as the model price table declining to model introductory pricing it cannot date. A provider that costs nothing reads as **free**, never as an untracked zero: "$0.00" from Edge and "$0.00" from an ElevenLabs run nobody measured are the same string for opposite reasons. Nothing to model for caching, since there is none - the same sentence spoken twice is billed twice, which is itself worth surfacing if a callout ever repeats itself in a loop.
  - [ ] Give the composition root a test harness - `AppHost` is where the app is actually assembled, and it has no tests at all: nothing constructs one, so every behaviour that lives in it is covered only by running the app. Two of the three faults found in one afternoon's hand-testing were in it - stale voice ids surviving a provider switch, and a voice list that never refetched when the key arrived - and both were provably wrong from settings alone once the decision was lifted out into Core. The seam worth having is that lift: decisions that are pure functions of settings belong where they can be asserted, leaving the root to wire things together. Not a rewrite, and not a mock of every dependency.
  - [ ] Ask for the keys on the first run that needs them - A fresh install has no language-model key, so the first thing a Commander does is find the right row in a surface with fourteen sections. This is the guided path: the language-model key, the voice key as optional, and INARA when that arrives. **Driven by state, never by a "have we done this?" flag** - the condition is *there is no usable language-model key*, which is also true for a Commander who restored a `data\` folder onto a new machine, because `secrets.json` is DPAPI-scoped and `SecretStore` treats an undecryptable value as absent and says so in the log. A flag would show this once on a machine that could not read its own secrets and never again. Reuses the existing secret rows rather than re-authoring them: the settings surface is descriptor-driven, and a parallel copy of these three fields is a second thing to keep in step and the one that drifts. What leaves the machine per key is **computed from `EgressDisclosure`, not written by hand here**, for the same reason the privacy section already computes it - hand-written copy goes stale and this is the one place a Commander is deciding whether to trust the thing. Not a wall: capabilities are state rather than guards (Phase 3), so declining every key leaves d47 running and typed rather than a dead app behind a form, and skipping the optional ones must not dead-end. A key is **verified, not merely stored** - the row makes the real call and says whether it worked, because a key that is wrong, revoked or pasted with a trailing newline is otherwise indistinguishable from a key that works until the first turn fails; and this is where `AppHost`'s known fault lives, where a voice list did not refetch when the key arrived, so entering a key has to take effect without a restart. Paste-friendly and trimmed, masked with a reveal, and **never logged at any level**. Re-openable from About afterwards, since keys get rotated and revoked and the state that triggers this is a state a working install can return to.

  - [ ] Follow the live log, or stop following it - A floating jump-to-latest control with follow and scroll-lock, so reading history does not mean fighting new lines as they arrive.
  - [ ] Live log selectable and copyable - Read back what was said and copy it out. Free-form drag-selection across a continuously appending log is the hard part; rendering it as one read-only block is the way around it. If it is free due to the nature of the controls being used, then don't invent a workflow that's unneeded.
  - [ ] Copy log - One affordance for copying the entire session's log as currently filtered.
  - [x] Check for Updates on start - On start, when a new release is available, the user is given an opportunity to exit, install it, and restart.
  - [x] A real installer, not an archive - `d47-setup.exe` is the normal way in, with the zip still published for portable use and still what the in-app updater fetches. Per-user into `%LOCALAPPDATA%\Programs\d47` at `PrivilegesRequired=lowest`, so the no-elevation property survives; a proper Add/Remove Programs entry; rerunning a newer installer upgrades in place rather than stacking a second copy. The install directory is fixed rather than versioned, which is the reason Squirrel and Velopack are not used despite otherwise fitting: they install into per-version folders, so the exe moves on every update and orphans the `data\` folder beside it - the Commander's keys, settings and a several-hundred-megabyte model. Uninstall asks once before removing `data\` and defaults to keeping it, because none of that is recoverable by reinstalling. The Start Menu entry is written to exactly the path `StartMenuShortcut` tests, so the app's own offer stands down with no notion of having been installed. Pulled forward out of order: it was drafted for later in this phase, and the Commander was unpacking archives by hand in the meantime, which is a poor reason to wait. Not covered: code signing, so SmartScreen still warns - that needs a certificate and is a spending decision, not a build one.

- [ ] **Phase 18 — HOTAS switches**
  - [ ] Read the Commander's controllers - `Windows.Gaming.Input.RawGameController` reads button state from the desktop process with no driver, no window and no elevation, which is what keeps this inside the per-user no-elevation install and off the vJoy/ViGEmBus row in architecture.md §10. The device list is not a startup query: it fills in over time, and the spike's first reader waited for it to become non-empty and confidently reported three of six devices. The reader waits for the count to settle and stays subscribed afterwards, since hot-plug and slow enumeration are the same code path. Hardware lives in App behind an interface; Core sees settled switch positions through a `Poll()` in the same shape as the journal reader, so the replay harness can drive a switch without a stick attached. Findings in [docs/spikes/hotas-switch-read.md](docs/spikes/hotas-switch-read.md).
  - [ ] Assign a switch by flipping it - The settings row says *flip the switch you want and leave it there*, samples after a settle delay, and stores what it saw. There is no per-device profile table because none can be authored: Windows reports `HID-compliant game controller` for every device on the bench, so nothing exists for a human to key a table to. The instruction carries the classification — a maintained switch is still held when the sample lands, a spring-return one has gone home — because hold duration cannot do it. Measured, switch flips ran 407-1611 ms against push buttons at 206-1751 ms, so the ranges overlap outright and any threshold is a coin toss. A spring-return switch or a hat is declined with the reason rather than accepted and left to behave oddly.
  - [ ] A switch position means a state, not a press - The flip is the question and the game's own status is the answer: on a flip, d47 asks whether Elite is already in the state that position means, and presses the Commander's binding once only if it is not. Gear already down from a voice command and the switch moved to down does nothing at all, which is the entire point — every existing remapper is edge-triggered and blind, and that is why a maintained switch desyncs the first time the game changes its own mind on docking or a relog. Between flips nothing is touched, so voice, the game's own automation and the switch never fight. This is not an autonomous action: the Commander flipping a switch is the Commander asking. A maintained switch holds exactly one button per position including centre, so the input is an index rather than a boolean and there is no null state to special-case. Mode-gated by the same `ControlContext` that decides what is worth advertising, and reachable from the panel only — never from the tool surface, because a hostile in-game message must not be able to remap a switch.
  - [ ] A mapping that no longer fits its device says so - Stored against `NonRoamableId`, never against VID+PID. Turning 4x32 mode on or off renumbers every button on the throttle while leaving VID+PID identical, so a VID+PID key produces exactly the silent misfire this is meant to prevent, whereas the non-roamable id changes and the mapping fails closed. The row then asks to be reassigned instead of driving whatever now sits at that index.
  - [ ] Stop reconciling a switch that something else is driving - If a reconcile is followed immediately by an unexplained change back the other way, something else is bound to that action, and d47 pauses that switch and says so. Detecting the cause statically is not possible — with SimApp Pro or Joystick Gremlin in play, Elite's binds name a vJoy device that cannot be traced back to the physical switch — so this watches for the symptom instead, which also catches the leftover binding and the case nobody has thought of.
  - [ ] Show which switches disagree with the game - A stale switch is harmless under the rule above and costs one extra flip, but only if the Commander can see it coming. The panel and the VR surface show which assigned switches currently sit against the game's state. This is the answer real aviation reached with annunciators rather than servos, for the same reason: showing the state is cheap and moving the switch is not.
