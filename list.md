# TheApp - Capability Checklist

- [x] **Phase 1 — Foundation**
  - [x] TheApp installs on a clean machine - Installability treated as a 0.1.0 feature rather than a packaging afterthought, so no source-mode path ever diverges from the installed one. Per-user install, no elevation, unsigned with a published SHA-256, and one self-contained file with no runtime prerequisite. Not statically linked in the C sense - native libraries self-extract on first run - because architecture.md §9 shows that phrase has no clean referent in .NET, and NativeAOT stays deferred until the native dependency set is stable.
  - [x] TheApp keeps your key and your state safe - Settings survive a restart, unknown keys are rejected, and everything writable lives in one folder beside the executable. Two stores because one loader cannot both fail loudly and shrug; writes go to a `.writing` sibling then an atomic move, and secrets are DPAPI-encrypted at rest.
  - [x] TheApp says what went wrong - Levels, one target per subsystem, structured fields, and two sinks - one human-readable, one machine-readable so an agent can parse a session. No telemetry leaves the machine: no analytics, no metrics endpoint, no upload. Provider traffic is a separate claim with a separate row, because INARA, a cloud LLM, a paid TTS and web search all send journal-derived content off the machine when enabled.
  - [x] Turn a subsystem up without restarting - Runtime per-subsystem verbosity control.
  - [x] TheApp calls a capability - A request produces a real tool call that runs and returns a result, covering the capability registry and the descriptor declaring identity, tools, help, settings rows and display model. Descriptors are registered once and never mutated, and every tool profile's schema block is byte-identical across turns, so prompt caching survives a mode change.
  - [x] Every capability has a documentation page - CI fails if a registered capability has no documentation page, making "write the docs later" impossible rather than merely discouraged. Pages are written from real artifacts and must quote at least one code block or line of real output.
  - [x] GitHub Pages documentation - Each capability should have a documentation page. General help for TheApp outside of the particular capabilities is also available.

- [x] **Phase 2 — Journal spine**
  - [x] Journal behavior is testable without the game - A recorded session replays deterministically at 1x and 100x with no game, headset or hardware. Fixtures are byte-preserved via `.gitattributes` and scrubbed of the Commander name and real system visits, since the repository is public.
  - [x] TheApp knows where you are - TheApp answers what system you are in from the journal as part of an ordinary turn. Picks the newest journal by ordinal filename sort, opens shared for read/write/delete since Elite holds the file open, and is pull-based with no internal thread, which is what makes it testable.
  - [x] Survive a journal schema change - Elite adds and changes journal events several times a year. Unknown events are logged and skipped, a parse failure never kills the tail loop, and the machine-readable sink makes the diff findable, so a game patch costs a morning rather than an outage.
  - [x] Handle more than one Commander on a machine - A second Commander's journals must not merge into the first one's fleet, materials or location. The Commander is identified from the journal header and all derived state is kept per Commander, because a naive newest-file reader silently blends two people into one.

- [x] **Phase 3 — First conversation (typed)**
  - [x] TheApp answers a typed question - Type a question into TheApp's window and get a streamed reply from the model.
  - [x] Ship's AI Unsure - An explicit "unsure" result instead of a confidence threshold, because models produce confident-sounding scores that do not mean anything. A model-free keyword router ships alongside so the whole path is exercisable without a model.
  - [x] Capabilities as state, not guard - For example, an LLM or TTS experiencing downtime or token depletion flips a capability off and the next turn reads what is currently available, so there is no failure handler to author or keep in register. It falls out that every input path must be answerable with no capabilities at all.
  - [x] Model Level and Thinking - LLM attempts to gauge per-turn thinking effort from low through max, but no "off" unless the LLM is set to "none" or through transient degradation.
  - [x] LLM Turn Price - Per-turn token usage including cache reads, priced from a table, plus a running total. A profile switch is the only sanctioned cause of a cold prefix, so an unexplained cache miss is a regression the running total can surface rather than hide.

- [x] **Phase 4 — Settings surface**
  - [x] TheApp is configured without manually editing a file - Every setting, including the voice, is changeable in the UI with no hand-editing. Rows are generated from capability descriptors, defaults appear as placeholders rather than values, keys are write-only, and safety-critical rows are protected from the model.
  - [x] Apply every setting without a restart - Changing a setting takes effect immediately (no need to manually "save").
  - [x] Offer one searchable picker everywhere a value is chosen - A command-palette style picker with keyboard navigation, reused for voices, models and devices. Fail-soft by contract: with an empty list you can still keep the current value or type one.
  - [x] Show the controls the active provider actually has - Settings adapt to the selected provider instead of showing a hardwired set, and changing an endpoint resets the model list to that endpoint's namespace rather than leaving a stale selection.
  - [x] Settings only expose specifics of a provider (LLM, TTS, STT), such as selected voice(s), Model, etc. for the currently selected provider.
  - [x] Protect safety-critical settings from the model - Rows gating keyboard actions and macros are marked protected: never changeable through a tool the model can call, because the model consumes untrusted text and a guard it can flip is privilege escalation. Protected is a property of the caller, not of the modality. The panel, a hotkey and the model-free keyword router all reach these rows; the LLM path does not.
  - [x] Say what each provider receives - A settings row and a documentation page stating exactly what leaves the machine for each enabled provider: system and station names to INARA, turn text and game context to a cloud LLM, reply text to a paid TTS, query text to web search. What is currently leaving is answerable at any time, and every destination can be turned off. Amended in Phase 12: this used to promise local-only operation as a named configuration, which priced every later feature against a slogan rather than against the enumeration - what is owed is that nothing reaches a network without appearing in the list.
  - [x] Link each settings row to its documentation - A setup-guide link per settings row pointing at that setting's page. In-app help stays the short form; the page is the long form.
  - [x] Collapse settings cards - Collapsible sections whose collapse state is remembered as a view preference, not a setting, and applied before first paint so a collapsed card never flashes open.
  - [x] Settings Nav Menu - Is present and highlights the section based on the topmost visible setting.
  - [x] Hotkey Binding - (Only in main window) Press the key to bind it.
  - [x] Themes - Dark, light, default Elite-flavored, Guardian, and based on the current Elite Color Scheme palette, with color living in one place so no view hardcodes a literal.

- [x] **Phase 5 — Speaking**
  - [x] One audio stream - Everything audible goes through one queue with priority and supersede, including audio cues, so ducking, interruption and captioning need no second mechanism. One arbiter for every voice, because separate paths per voice are how a line gets spoken in the wrong one. The arbiter exposes a render-side reference tap from the start, since echo cancellation needs the far-end signal and retrofitting that tap means opening the one component every voice path depends on.
  - [x] TheApp speaks its answer aloud - The reply is audible in the chosen voice. Synthesis is sentence-chunked so speaking starts at the first sentence boundary - the largest perceived-latency win available.
  - [x] Say so when the model is misconfigured - An audible warning when the provider setup is wrong, rather than silence that is indistinguishable from a model with nothing to say.
  - [x] Say something when a turn is taking too long - Retry with backoff (N tries, X wait, sequential or logarithmic), and if exceeded say so aloud in the current voice rather than leaving silence.
  - [x] #20 Give every loop state its own audio cue - One default per state. Cue names come from the shipped resources rather than a hand-written table, since a wrong name goes wrong as silence nobody notices.
  - [x] #18 Play a thinking bed while the model works - Audible evidence that TheApp heard you and is working, instead of dead air while a turn runs.
  - [x] Stop - An always-available instant silence that supersedes everything on the queue and stops mid-sentence, reachable by voice and by hotkey and never gated behind a turn completing. A companion that talks is only tolerable if it can be silenced faster than it can finish a sentence.

- [x] **Phase 6 — Listening**
  - [x] Choose the microphone in settings - Pick the input device instead of inheriting the system default. A blank selection produces a silent default and a turn reporting no speech detected, with nothing indicating why.
  - [x] PTT - Hold the key, speak, release, and your words appear. The key-down path awaits nothing before recording starts, and push-to-talk is one gate policy over an audio stream so continuous listening and wake word become later policies rather than a rewrite. May be set as a "toggle" rather than true PTT via settings.
  - [x] STT Model Choice - Commander can choose which Whisper model to use and whether or not to allow it to run on the GPU. In VR the GPU is already the scarce resource, so a large model running there surfaces as dropped frames and reprojection rather than as anything that looks like a speech problem, which is the hardest kind of setting to diagnose. GPU is opt-in with that cost stated on the row, and the default is CPU whenever a headset is present - a short push-to-talk clip on the small English models absorbs that fine.
  - [x] Bias transcription with proper nouns from the journal - Feed system, station and ship names from the journal into the transcriber so they come back spelled correctly. Journal-derived and network-free; proper nouns are where speech recognition fails hardest and most silently.
  - [x] Report a key that is bound twice - A double-bound push-to-talk key currently has no symptom other than not working; detect the collision and say so. Reads the same parsed binds as keyboard-action reachability rather than keeping a second view of the Commander's controls.
  - [x] Settings by voice - Unless otherwise noted, every setting should be settable by voice. Protected rows are reachable by voice only through the model-free keyword router, so "by voice" never silently means "by the LLM."
  - [x] Answer what can you do, from the registry - Spoken help projected from the capability registry - groups, then capabilities, then detail and example phrasings - ranked by real usage. The model is never asked what TheApp can do, because asking produces confidently invented capabilities.

- [x] **Phase 7 — Knowing the game**
  - [x] Know what is happening around you - Live situational awareness attached to each turn: where you are, what you are flying, and what just happened.
  - [x] Know your location and your carrier (if owned) - Current system, station and body, plus where your fleet carrier is.
  - [x] Ship's loadout - Modules and stats from the loadout event.
  - [x] Ship metrics - Base jump range and similar, computed from what the loadout event actually reports rather than from a table of ship specifications.
  - [x] Know what ships you own and where they are - A fleet registry built from stored-ships journal events.
  - [x] Know what materials you are carrying - Materials inventory built from journal events, answerable without an external lookup.
  - [x] Know what is in your backpack and ship locker - On-foot inventory parsed from the local files Elite writes.
  - [x] Session summary - Earnings, bounties, exploration data sold, materials gained and jumps made since the session began, built from the journal already being tailed rather than from anything new.

- [x] **Phase 8 — Proactive speech**
  - [x] Call out danger without waiting for a turn - Interdiction, shields down, hull damage, dangerous heat and a full cargo hold announce themselves from journal and Status.json events. These fire on the event and never at the model's discretion, because an alert that depends on a turn completing is not an alert.
  - [x] Fuel and range safety - Low-fuel warning against the current tank, plus the case that actually strands a Commander: the next star on the route is unscoopable and the one after it is out of range. The journal and the route file supply both, and the warning is unconditional rather than something the model may decide is not worth mentioning.
  - [x] Route Progress - Jumps remaining (every N systems (setting)), next system, neutron and white-dwarf hazards ahead, and scoopable-star ambiguity resolved rather than guessed. Reads the route file Elite writes locally, so no route-planning service is needed.
  - [x] Remark on an unusually long jump - Flavor during a longer-than-normal hyperspace jump, fired once hyperspace has actually been entered rather than on the jump being initiated. Threshold is configurable but defaults to 30 seconds.
  - [x] Recognize where you have arrived - Place-aware callouts for engineer bases, notable stations.
  - [x] Home System - Home callout when you arrive in your home system (setting).
  - [x] Call out material-gathering milestones - The first unit, then 25/50/75%, a running count above 75%, and full. The tracker is primed from the session backlog at startup; otherwise starting TheApp after Elite means the milestones never fire.

- [x] **Phase 9 — VR**
  - [x] Order agnostic Overlay - The order of starting SteamVR, Elite Dangerous, TheApp, doesn't matter.
  - [x] TheApp appears in the headset - Captions render over Elite in VR through OpenVR (Elite never calls OpenXR) and clear on their own. Captions are their own unmovable, output-only, ephemeral layer with a rolling three-line window timed from the end of speech. Captions follow Netflix CC standard.
  - [x] Configure the captions - Follows Netflix CC standards.
  - [x] TheApp's panel works in VR - One widget tree renders to both the desktop window and VR, so the windowed UI can never be more functional than the headset one. Mini is a mode of the same panel - a reduced content set - not a separate surface or a scaled-down copy.
  - [x] VR Panel locking - Head-locked or world-locked placement, per surface. Choosing world-locked implies re-anchor is bound and reachable off-panel.
  - [x] Re-anchor the panels - Elite's in-game recenter moves the cockpit without telling SteamVR, so world-locked surfaces drift out of position with no event to hook. A Commander-triggered re-anchor snaps every world-locked surface back to current head pose and preserves their relative layout rather than stacking them. Reachable by voice and by hotkey, never only from the panel, because a drifted panel is precisely the case where you cannot aim at it. Head-locked surfaces and the caption layer are unaffected.
  - [x] Overlay Positioning & Look - Opacity, curvature, distance, size, and scale, configurable per surface.
  - [x] Panels can switch between curved and flat - The panel is bent {curve setting} around the Commander.
  - [x] Open at a size that fits the screen - Avalonia already matches the monitor's scaling: Width and Height are device-independent pixels, so the 820x640 default is 1230x960 actual pixels at 150%. That is the problem rather than the fix - it is nearly the whole usable height of a 1080p display and taller than a 1366x768 laptop screen outright, because the default was chosen at 100% and never checked against a scaled work area. The opening size is clamped to the working area of the screen it actually appears on, and the size and position the Commander leaves it at are remembered like the panel's collapse state already is, so the default only ever has to be right once.
  - [x] Zoom the desktop window - Ctrl and the scroll wheel, Ctrl+plus, Ctrl+minus, and Ctrl+0 for 100%, because every browser has already taught the Commander those four gestures and a panel that invents its own is a panel they have to be told about. Scales the rendered panel rather than restyling its text, so layout and spacing survive at any level, and it applies to the settings window too since that is the same widget tree. The level persists between sessions like the theme does. This is a desktop item living in a VR phase: its natural home was Phase 4 and that phase is closed, and it belongs beside *Scale the big panel* anyway - shipping a zoom for the headset and none for the window makes the windowed surface the lesser of the two, which is the same parity the one-widget-tree item is protecting from the other direction.
  - [x] Scale the big panel - Zoom the panel up and down in the headset, distinct from mini mode, which reduces content rather than shrinking the rendering.
  - [x] Keep working when the main window is minimized - In 2D or in VR, if TheApp is minimized, all 2D, VR, and voice functionality still works.

- [x] **Phase 10 — Acting on the game**
  - [x] Know which actions the Commander can actually reach - Parse the binds file and know which in-game actions have a keyboard binding at all, because the audience is HOTAS-heavy and a stick-only action asked for by voice fails as silence. Unbound actions are excluded from the advertised profile and asking for one gets a spoken reason instead of nothing. Read-only: TheApp never writes the Commander's bindings.
  - [x] Autonomous actions are opt-in per action - Every other capability acts on something the Commander said. An action that fires a game input on a journal event with nobody asking is a different category and needs its own consent, so each one is off by default and enabled individually. The category gets its rule before the second member of it exists.
  - [x] TheApp honks (discovery scanner) when you arrive in a system - The discovery scanner fires on entering a system using the Commander's own key binding, injected via scancodes with the Elite window focused. Never installs a low-level keyboard hook, and `release_all()` is unconditional because a stranded key here is a throttle that will not stop. The first member of the autonomous-action category and therefore off by default and enabled on its own row.
  - [x] Offer only the actions that work right now - Mode-gated action advertisement, so the set differs on foot, in the SRV, in supercruise and in normal space. The cockpit is not one mode: hardpoints, cargo scoop and landing gear do nothing in supercruise, and Status.json flags supply the split for free. The model is never told about a key that currently does nothing, whether the reason is the mode or the absence of a binding.
  - [x] Decide which tools ship on a turn as the count grows - At some capability count the tool schemas stop fitting comfortably in context and something must choose between them. The choice is between pre-declared profiles, not between individual tools, so budget pressure degrades to a smaller profile instead of destroying caching on the exact turn caching starts to matter. Whatever is chosen, the anti-invention guardrails are static prompt material and must never be strippable by a budget or effort setting.
  - [x] Control flight and navigation by voice - Landing gear, lights, cargo scoop, hardpoints and the frame shift drive.
  - [x] Control ship systems by voice - Power distribution, fuel scoop, silent running and heat sinks.
  - [x] Control panels, UI, and fire groups by voice - Cycle the panels and fire groups without taking a hand off the stick.
  - [x] Control the SRV by voice - Toggles only (turret, forward/back, dismiss/recall ship, board, exit SRV, etc.).
  - [x] Put something on the clipboard - A system name, route or value placed on the clipboard so it can be pasted into the game or a browser.
  - [x] Galaxy Map - Set a course by sending keystrokes to the in-game galaxy map. Best-effort rather than guaranteed, since it depends on map focus, layout and the game's language setting, so the clipboard route is the primary path and auto-plot is the convenience layered on top of it. A failed plot says so rather than leaving the Commander believing a course is set.
  - [x] Send/Receive messages to another commander or commanders - Dictate into Elite's chat: local, wing, system.
  - [x] Macros - Named multi-step voice-triggered sequences, validated against closed vocabularies and the action allowlist. Invocation is by voice; authoring is not, because composing a new action sequence is the one input whose vocabulary cannot be closed in advance. This is the exception to "every setting can be set by voice."

Using LLM (if available), a sensible voice is chosen for each persona based on the persona's prompt (or custom prompt) in the background, so picking a character does not also mean auditioning potentially hundreds of voices.
  - [x] Ambient Voice - In-character ambient lines motivated by live game state, varied (by LLM if available, otherwise by initially the 10 generated stock phrases per game state covered).

- [x] **Phase 12 — Soundscape**
  - [x] Three pages for the transcript - The big text area is one of three pages, chosen by tabs along the top of it: **Conversation** (the Commander and the ship's AI, and nothing else), **Technical** (the same with the diagnostics left in, which is what the panel always showed), and **Log file** (today's log, read when the page is opened). The split rests on the caller naming the kind of line as it writes it, because it is not recoverable afterwards - a version banner and a reply are both text, and separating them by pattern is guessing at somebody's prose. The page is a property of the surface like `PanelMode` is, and for the same reason: both surfaces bind one model, so a page held there would send the headset to the log the moment the window went to it. Mini shows no tabs, being the tail and the provenance line and nothing else. They have to read as tabs rather than as buttons or links, which is a property of the join and not of the label: the selected one shares the panel's fill and drops the border where they meet. Verify by looking at the captures.
  - [x] One type scale, and d47's own text sized to match its controls - A row's label reads smaller than the value it labels: every control renders at the framework default of 14 while d47 sets its own text by hand at 10 to 13, so a label is 13, its help is 11, and the combo box beside them is 14. The fix is to raise ours rather than shrink the controls - a settings surface is read at a glance from a metre away in a headset, and the answer to that is never less type. Forty-six size literals across seven files with nothing naming them is why they drifted apart in the first place, so this replaces them with a scale named by role - heading, subheading, body, secondary, small - and body is whatever the controls are. Touches `PanelView` as well as the settings surface, since the avatar landed there in Phase 11, and both surfaces have to move together or the headset and the window disagree about what a label looks like. Verify by looking at the render captures across themes at more than one zoom level: the failure this is fixing was visible in a screenshot and invisible to every test.
  - [x] **Settings is a tab of the main window, not a second window** - One visible window. Settings becomes another tab in the strip that already carries Conversation, Technical and Log file, and takes the place of the big multiline text area when it is selected; the Ask line below it gives way to the settings footer, which is where the storage line and its own controls already live. The short-lived modals stay modal - About, confirm, the picker, hotkey capture. The plumbing is nearly free: `SettingsView` is a window-agnostic `UserControl`, every dialog it opens takes its owner from `TopLevel.GetTopLevel(this)` and re-parents, and the second `ZoomHost` and window-placement slot both retire. The real work is width: the settings surface is a 224px nav column plus a 700px minimum and opens at 1180, against a panel window of 820 meant to sit beside a running game - so the nav column has to collapse below about 900, or the second window has not been removed so much as the first one made too big to keep on screen. Two behaviours need deciding rather than porting: what Escape does when there is nothing to close, and hotkey capture now tunnelling on the same top level that carries the open-settings and focus-ask gestures. The VR overlay renders the panel and must not gain a settings surface it was never sized for - mini already hides the tab strip, and full has to keep the tab out of the headset rather than showing a 1180px column at a metre.
  - [x] Search whichever tab you are looking at - One search affordance for the main window, on the tab that is selected: Conversation, Technical, Log file, and Settings once it is a tab rather than a window. One control and one gesture, not four features bolted to four pages - Ctrl+F focuses it, Escape clears it and gives the page back. What a match *does* differs by page and that difference is the design rather than an inconsistency: the transcript pages are prose, so a query highlights every hit, says how many there are and steps through them, leaving the surrounding lines in place because reading back a conversation means reading what was around it; Settings is 92 rows across 14 sections, so a query **filters** - rows whose label, help text or key match - and the nav column shows only the sections still holding something, since highlighting in place in a haystack is a scroll hunt with extra colour. The query belongs to the page and is dropped when the page changes, because one string that filters here and highlights there is a control that behaves differently depending on where you last clicked. Must not fight the log arriving underneath it - a hit found in the live log stays found as lines append, which is the same problem *Follow the live log* solves and should use whatever answer that reaches. Desktop only: the headset has no keyboard, mini shows no tab strip, and a search box the Commander cannot type into is worse than no search at all.
  - [x] Anything that might take a moment says it is working - The rule already written into the picker button - "a button that looks unchanged for a second reads as a button that did not take the click" - applied everywhere it is true rather than at the one place it was noticed. Opening the Log file tab reads a file off disk; a model list, a voice list and a key verification each cross the network; a gap reaction spends a model round trip before the core says its first word. Each of those can look exactly like nothing happening. **The affordance that was touched is the thing that shows it** - the tab, the button, the row - never a spinner somewhere else on the surface, because a Commander who clicked here does not look there. Reuse `BusyGlyph`, which exists for this. Two failure modes to hold off at once: no silence on the slow case, and **no flash on the fast one** - an operation that finishes in 40ms must not strobe, which means a short delay before showing and a minimum time on screen once shown, and those two numbers stated in one place rather than chosen per call site. The control shuts while it works, as the picker's already does, so a second click cannot queue a second copy of the same fetch. Written as something a call site opts into in one line, not as a pattern to be reimplemented: the next long operation is the one that will ship without it. Verify from the captures - both surfaces, because the headset shows the same widget tree and a glyph that only animates on the desktop is half an answer.
  - [x] #96 Ambient audio mixer - Per-category levels and mute, plus how each category ducks against speech.
  - [x] Custom Sound Cues - Drop in your own audio files and have TheApp use them, kept distinct from the set TheApp ships with.
  - [x] Ambient music - Music separate from cues and sound effects, with its own level and its own ducking behavior against speech. Ambience is situational based on journal or "general."
  - [x] Pick up dropped-in audio without a restart - Cues, sound effects, music and ambient content discovered from convention folders and reloaded live.

- [x] **Phase 13 — Hands-free listening**
  - [x] Echo Cancellation - Acoustic echo cancellation, for continuous listening and natural interruption. Consumes the render reference tap from the single audio arbiter rather than a loopback capture, which is both lower latency and correctly aligned. WebRTC AEC3 is BSD-3. The tap was built in Phase 5 with nothing subscribed to it precisely so this would be one subscription rather than surgery on the component every voice path depends on, and it was: `EchoCanceller` is framing either side of the module and nothing else, since WASAPI hands over whatever buffer size it likes and AEC3 takes exactly 10 ms. Measured against a simulated room with a 60 ms path, upwards of 25 dB removed with the near end kept within a few dB through double-talk — which is the half that matters, because a canceller that solved the problem by going deaf while d47 speaks would pass the first measurement and deliver none of the point of it. Two findings worth keeping: a **harmonic** far end defeats the delay estimator outright, so a test written with a sine wave in it measures nothing; and whether the canceller is running has to be read from the canceller rather than from the row that asked for it, because that boolean is what decides whether hands-free listening stays open while d47 talks. Uncancelled, it does not — half duplex is the honest fallback and the row says so. The disposal is the sharp edge: applying a settings row frees the module from one thread while two audio threads are inside it, and that is a native access violation rather than an exception — nothing catches it and the process simply goes. So every native call and the disposal share one lock, which costs the render and capture overlap the module would have allowed and buys the safety by construction rather than by timing. A concurrency test found the other half of the same mistake within seconds: the module was published before its stream configs, so a frame could arrive, see a module, and dereference a config that did not exist yet.
  - [x] Voice Activity Detection (VAD) - (An option) Voice activity detection as a continuous-listening gate policy over the existing stream. Phase 6's "one gate policy over a continuous stream" was written as a promise about this phase and it held: a detector on the same `Write` path, opening the same gate, with the same pre-roll covering its onset delay that already covered the polling delay on the key. **The adaptive noise floor is the whole design** — an absolute threshold is what makes every energy VAD either deaf on a quiet microphone or permanently open on a loud one, because "loud enough to be speech" is a property of a gain that varies by tens of decibels across the interfaces this will meet. So the floor follows the room, falling fast and rising slowly, frozen while somebody is talking so a long sentence cannot drag it up to meet itself, seeded from the first frame rather than climbing from silence, and floored absolutely so a muted device cannot make speech out of its own dither. The detector decides on the audio thread and the **tick thread acts on it**: opening plays a cue and closing hands an utterance to a transcriber, and neither belongs on a real-time callback. The key stays live in every mode and outranks the detector.
  - [x] Wake Word - Wake-word gating, implemented as another gate policy over the same audio stream. **It matches words rather than audio**, which is the design and not a shortcut: d47 already has a speech model and a detector that says where a sentence started and stopped, so the wake word is the cheapest possible thing on top of both — no second model to ship, no second download, no vocabulary fixed at build time, and no keyword that cannot be the name the Commander gave their ship's AI. Leave the row unset and it *is* that name, so renaming the core renames the wake word. Matching is deliberately forgiving, on a form with punctuation and spacing removed, because Whisper writes a short name however it hears it — `D47`, `D 47`, `d-47` are one word — and the name has to be near the front, since talking about d47 is not talking to it. The name alone wakes rather than asks: the listening cue sounds, and a window opens in which the next sentence needs no name, because that is how a person addresses anybody. The cue rather than the loop state behind it — entering Listening would be accurate for as long as the window lasted and then stuck, since nothing settles out of that state, so a Commander who said the name and changed their mind would leave the face listening for the rest of the session. What is waiting is the microphone, and the microphone has an indicator of its own now. The cost is stated rather than hidden: everything said in the room is transcribed before it can be discarded, so this wants one of the smaller models.
  - [x] Show that the microphone is open - Once wake word or VAD means continuous capture, listening state is visible on both the panel and the VR surface. Continuous capture with no visible state is the thing a user is right to distrust, and the indicator is a property of the gate policy rather than of any one capability. Three states rather than two, because the honest inventory has three: **open** and keeping what it hears, **armed** and deciding for itself, and **idle** — the device open with nothing kept, which is what push-to-talk has always quietly done and never shown. Filled or hollow says which before colour does. It lives in the row that carries the provenance line rather than in the header, because the header is what mini takes away and mini is the headset's normal state — and a Commander in a headset has no window to go and check.

- [x] **Phase 14 — Knowledge and external data**
  - [x] Galaxy Search - Systems, stations and bodies, distances computed from coordinates. Query parameters are validated locally because the search service ignores filter keys it does not recognize. **Measured, and worse than stated:** a *misspelled* real filter is ignored exactly as a bogus one is — `allegience` returned the same 108 systems as no filter at all where `allegiance` returned 60 — so the dangerous case is not a typo'd request failing, it is a typo'd request succeeding and reading like a filtered answer. A wrong *value* shape is a loud 400; a wrong *key* is a confident answer to a question nobody asked. Hence a closed vocabulary in Core, checked before a request is built. The other half of the item is the projection: one system record is 268 KB and a three-result search is 44 KB, so what reaches the model is six fields per system and the raw record never leaves the client. Distances are computed from coordinates here, because there is no lookup-by-name endpoint at all — `api/system/name/…` is a 404 — so a spoken name becomes a position by naming it as a *search reference* and reading back what it resolved to.
  - [x] Find Nearest - Nearest module, nearest ship for sale, stored ships and modules, plus body and signal lookups. Module and ship names are matched against the real catalogue (48 ships, 132 modules, read from the service's own `field_values` on 2026-08-14) before a request is built. The catalogue is validated but deliberately **not advertised** — an `enum` that large sits in prompt position 1 where one byte invalidates the whole cached prefix, so the parameter is free text and the matching happens locally. It handles both ways a spoken name arrives wrong: a fragment ("shield generator") and a transcriber's misspelling ("Frame Shift Drve"). Stock age is part of every answer, because outfitting is crowd-reported — a live search returned a carrier last reported in 2024 beside stations reported that morning. Stored *ships* came from the fleet tool in an earlier phase; stored *modules* are now `get_stored_modules`, folded from `StoredModules` and grouped by where each one is with what fetching it costs — read off disk, so it answers with the galaxy search switched off, which is what a fresh install is. **Three wire shapes, and two of them lie.** The station `modules` filter is a *group* whose members each take their own value array, and the flat spelling is silently ignored exactly as a bad system filter key is: the group shape returned 3,402 stations where the flat shape returned the unfiltered 10,000. The body `signals` filter is a *third* shape — `{"name":{"value":["Biological"]},"count":2}`, a choice member beside a bare number — and the range spelling returned the unfiltered 1,315 bodies within 20 ly of Sol. Worse, `count` is **exact rather than a minimum**: 1 returned 41 bodies, 2 returned 14, 3 returned none and 4 returned 2, each carrying precisely the number asked for, so the tool says "exactly how many" — a "three or more" that quietly meant "exactly three" is a wrong answer that reads like a right one. `distance_to_arrival` is read off every result and **never offered as a filter**, because the service ignores it: 0-10 light seconds returned the same 1,315 bodies as no filter at all. Body types are matched rather than listed (61 of them) and the matcher now takes a *unique* fragment — "earth-like" names exactly one subtype and is what a person says, while "gas giant" names six and is refused with the candidates rather than answered about whichever came first.
  - [x] Route Planning - Neutron and long-range plotting, trade loops, Road to Riches, and mining routes. A plot is a different protocol from a search — submitted, queued and polled — so it is its own seam and its own capability, sharing the galaxy search's one setting because it is the same host and the same decision. Measured on 2026-08-14: Sol to Colonia came back on the third poll, a Road to Riches loop on the first, a four-hop trade route in forty-eight seconds; hence a ninety-second budget against a search's fifteen, and a sentence saying what to shorten when it runs out. **Efficiency is backwards from its name** — it is how strictly the plotter holds to the direct line, so lower wanders further, finds more neutron stars and finishes in fewer jumps: 10 took 156 jumps, 25 took 157, 60 took 168, and 100 was accepted and then found no route at all, which is why it is clamped to 99. **The route endpoints echo back only the parameters they understood**, which is a local oracle the search endpoints do not offer and how every name here was established rather than guessed: `capital`, `cargo_capacity`, `capacity` and `loop` are all silently dropped from a trade plot where `starting_capital` and `max_cargo` survive — and a dropped capital is not an error, it is a plot that finds nothing affordable and reads exactly like a correct answer about a Commander with no money. So the Galaxy Map goes first because it is the one that can be built without asking anybody, and **the contacts panel is gated on having asked Frontier** through the route [docs/spikes/screen-reading-licence-and-rules.md](docs/spikes/screen-reading-licence-and-rules.md) §6.6 names. Asking costs an email and settles a question that reading cannot. **A signal filter highlighted in the DSS is not on this list** — asking costs one sentence, is remembered, and works in the headset, so vision has to beat that and does not. Local matching only: a screenshot of Elite carries the Commander's name, their wing, and whatever is in the chat panel, so nothing leaves the machine and no frame reaches the model, which also keeps pixels off the untrusted-input path where an in-game message on screen would become text the model reads. The cheap signal gates the expensive one — `GuiFocus` says a panel is open, and only then does anything capture, so the whole subsystem is asleep except in the seconds it matters. **The failure mode is the reason this is last**: it breaks on a UI change, a resolution, an aspect ratio or a language, and a mismatch is a confident wrong answer rather than an error, which is the one thing every other rule in this file is written to prevent. It would also be the first input d47 reads that the game did not deliberately write down — everything else is a file Frontier publishes. **Two calls settled 2026-08-16, both recorded in [docs/plans/phase-22-reading-the-screen.md](docs/plans/phase-22-reading-the-screen.md).** The ask happens: the enquiry to `community@frontier.co.uk` is drafted at [docs/plans/phase-22-frontier-enquiry.md](docs/plans/phase-22-frontier-enquiry.md), it asks the two cases separately because they differ, and until it is answered nothing here reads other characters. And the OCR engine is **`Windows.Media.Ocr`**, which the spike recorded as a lead rather than a recommendation on the grounds that reaching WinRT projections meant a repo-wide framework change — an objection that was already spent when it was written, because Phase 21 moved `D47.App` to `net10.0-windows10.0.26100.0` the same day and App is the only project that could host an OCR call anyway. So it costs a `using` directive, carries no third-party licence, and leaves the ONNX Runtime / Eigen MPL-2.0 judgement undecided, which is where the spike wanted it. Whether it reads Elite's font is unmeasured and waits on a frame. One piece of product work is already known and is not built: **`GuiFocus` is parsed by nothing today** — `GameStatus` reads flags, fuel, cargo, heat, body, balance and position and stops — and it is the gate for every version of this phase, desktop or VR.

- [x] **Phase 23 — Systems worth remarking on**
  - [x] Know which systems carry lore - A table of systems that mean something beyond their astrography — HIP 12099 holding Jameson's Crash Site is the shape of it, and only the shape: the phase is the mechanism, not that entry. **The table holds the fact, not the prose**: *this system contains this notable site* is a fact about Elite Dangerous in the same category as which system an engineer sits in, and `Engineers.tsv` already ships that way — a generator with its provenance recorded, Frontier attributed in their own words through `NOTICE`, non-commercial, and keyed on **system address** rather than name. Nothing automated guards that: `PackageLicenceGateTests` covers packages, cannot be pointed at a data file, and `Knowledge/*.tsv` sits outside its scope by design. **But the rows being facts is not the whole question, and this is where the engineer precedent stops carrying.** The set of engineers is closed and defined by the game; *which systems are worth remarking on* is a judgement somebody made, so copying a community list copies their compilation even though every row in it is a fact. **Checked for a first-party set to key against instead, and there is none:** `CodexEntry` fires in 99 of the 913 corpus journals and is the discovery codex — "G Type Giant", "Terraformable" — astronomy rather than lore, and `ApproachSettlement` names 229 distinct settlements while saying nothing about which of them matter. So the shipped table is **short and written by the maintainer**, which is their compilation rather than somebody else's, and it is a seed rather than a corpus: the two items below are what grow it, on the Commander's own machine, out of what they actually asked about.
  - [x] Remark on arrival, and not again today - On `FSDJump` into a system the table knows, the core says something about it unprompted. **Once per system per 24 hours**, which is the whole difference between a companion and a tour guide who has forgotten meeting you. **Both of the things this was written as needing, d47 already has**, so it is a new member of an existing family rather than new machinery: `TickContext` carries an injected `DateTimeOffset Now` (`Ticking/TickLoop.cs:13`), which is the clock-free time source and already the pattern; `AmbientCallout` already keeps a `_lastSpokenAt` behind a settle window and a cooldown; and `SamplingStore` is the restart-surviving store, per Commander, keyed on `SystemAddress` and written through `AtomicFile`. What remains of the persistence question is the one `docs/plans/change-requests.md` already asks about `PersonaHost`'s in-memory `_introduced` set, and both are better answered once than twice. **It is a callout, not an autonomous action:** `AutonomousCapability` is one protected row per action because an action that fires a game input has no sentence of consent behind it, and this presses nothing — so it takes the callouts' settings shape rather than that one. Two things to get right rather than assume: the stored stamps are **absolute rather than elapsed**, or the replay harness at 100x makes "24 hours" mean nothing; and the window itself is measurable rather than a guess — 519 of the 913 corpus journals carry `FSDJump`, so how often a Commander re-enters the same system inside a day is a number `spike/CorpusReplay` can produce before anybody picks one.
  - [x] Look it up, and say where the answer came from - The remark arrives in two parts: first the bare fact the table holds — *this system contains this site* — then a web lookup, and when it returns, what it found. **Web Search already ships in the shape this needs**, and three things fall out of that. It is the provider's own server-side tool, so the model asks and what reaches d47 is prose in a turn. It therefore **opens no new destination**, and `EgressDisclosure`'s closed set gains no entry — which is not what a phase adding a network lookup normally costs. And its standing rule is that a result is **a sentence in the turn and never a row written into a shipped table**, which is this design's own split, already written down and already enforced by there being no code path that receives a row. **Availability is knowable before d47 opens its mouth** — `ILlmProvider.SupportsWebSearch` is gated on the provider's own endpoint (`Conversation/ILlmProvider.cs:62`) and `TurnLoop.WebSearchEnabled` is the toggle hook (`Conversation/TurnLoop.cs:197`) — so a Commander whose endpoint cannot search is told nothing further is coming rather than left waiting for a second part that never arrives. **Off, remark only, or remark and lookup:** three states rather than two independent switches, because a lookup with the remark off is detail about something that was never announced. A follow-up that arrives stale is **dropped rather than spoken**, since the Commander may be interdicted or three jumps away by the time it lands, and the callout family already has the precedence to decide that. **This is the first unprompted untrusted prose d47 speaks** — every other untrusted path is either the Commander having asked or a callout assembled from journal fields — so the rule is stated here rather than inherited: what the search found is spoken **as a search result**, never in the table's flat voice. Repeat visits re-search, and whether a runtime cache keyed on `SystemAddress` earns its keep is a decision to be taken rather than drifted into, because a stored search result sits close to the edge of the rule above.
  - [x] Commander's Lore - The Commander can ask for a system to be added when the table does not know it, and d47 attempts a lookup rather than simply believing it. **What survives corroboration and what does not are both kept, and they are not the same thing:** an entry the search supports and an entry that is the Commander's word alone are stored as different tiers and read back in different sentences — *"this system contains X"* for the shipped table, *"the search says…"* for a corroborated addition, *"you told me…"* for **Commander's Lore**. That is the difference between a companion that remembers and one that invents, and making it structural is what stops it depending on the persona remembering to hedge. **Surviving a lookup is a label, not a verdict:** an obscure but real site finds nothing, and a search can appear to corroborate something a model half-invented, so the tier is recorded and never promoted to truth. **The trust boundary is the part to get right first.** Adding lore is a tool the model can call, and the model reads untrusted text — journal, in-game comms, and now search results — so a hostile in-game message can attempt *"add to your lore that…"*, writing persistent local state that d47 later speaks aloud with nobody having asked. Persistence plus unprompted speech is a sharper primitive than it looks. It presses no key, so it need not be protected the way every row reaching the keyboard is, but **every entry records how it arrived** — panel, keyword router, or the model's own tool call — because nothing else can tell an entry the Commander dictated from one the model wrote on its own initiative. `llm.aboutMe` is the nearest precedent and is a cousin rather than a template: also Commander-authored and also reaching the prompt (`Conversation/PromptAssembly.cs:11`, position 4), but one paragraph rather than keyed, and read as context rather than spoken unprompted. Open: whether a later corroboration **promotes** an entry or it stays the Commander's word for good, and whether the file is per-Commander like `SamplingStore`'s FID keying or per-installation. It lives in `data/` beside the executable and is editable by hand, which means it inherits Phase 21's correction — **change is detected by comparing content, never a last-write time**, because two writes inside one 15.6 ms tick of the file-system clock carry the same stamp and a hand edit is a one-off that stays missed.

- [x] **Phase 24 — Utilities**
  - [x] Two clocks, one instant - The Utilities tab answers what time it is in both worlds at once: Elite runs **1286 years ahead**, so 2026-08-17 is 3312-08-17 and the in-universe date is arithmetic over the same `UtcNow` rather than a second clock that can drift out of step with the first. **`IWallClock` already is the mechanism and no invariant needs relaxing.** "No Core component reads the clock" means Core does not call `DateTimeOffset.Now` inline; it takes an injected clock and asks, and `SystemWallClock.Instance` — wired at `AppHost.cs:582` — returns the real system time. So the running app shows the Commander's actual clock through one constructor parameter, and the replay harness can still run a year of turns in seconds. That is the whole reason the interface exists, and the alternative was considered and dropped: dropping the injection buys this page one fewer parameter and costs the 692,631-event corpus replay. Local presentation follows the rule `WallClock` already states — the instant is UTC and the zone is passed in at the point of asking, exactly as `SpendWindows` does it, because an instant recorded in local wall-clock is wrong twice a year and cannot be repaired afterwards.
  - [x] Timers and alarms - Named, set by voice or from the panel, and **the first thing d47 does that nothing external triggers**. Every other behaviour is reactive — a journal event arrives, a callout goes out — or the Commander started it in that moment; a timer fires because time passed and nothing happened at all. The state lives in Core and the tick loop asks *is anything due* with the injected now, which keeps both the clock rule and the replay harness. **Alarms survive a restart and timers do not**, and that asymmetry is deliberate: an alarm for 07:00 is a promise about a wall-clock moment that outlives the process, and a forty-minute timer through a crash is a question nobody can answer — half elapsed, or start again? **An alarm that could not sound says so afterwards.** d47 cannot fire while it is closed, so a missed alarm is reported when it next starts, with when it was due, rather than either failing silently or sounding hours late as though nothing had happened. Stored in `data/` beside the executable, hand-editable, and change detected by comparing content rather than a last-write time — Phase 21's correction, because two writes inside one 15.6 ms tick of the file-system clock carry the same stamp.
  - [x] A timer says its own name - The alarm sound is a **shipped clip generated by a tool**, joining the `AlertCue` family and its `CueLibrary` contract: named for the enum member, with the test that asserts the shipped set matches the enum exactly, because a hand-written member-to-filename table is a place for a typo to live and a typo there goes wrong as silence. Runtime synthesis was the alternative and it was rejected for cost rather than taste — it would let each timer carry its own tone, which is genuinely useful in a headset where you cannot glance, but it is new machinery in the audio path for a distinction the voice already makes better. **So the cue says *something finished* and d47 speaks the name**, which is the same mechanism as the readback below and needs no per-timer sound at all. Everything goes through the one arbiter like all other audio, which is what decides whether a chime waits for a sentence to end or lands on top of it.
  - [x] Ask the app, not the model - "What's the date?" is answered by the **keyword router**, deterministically, with no turn taken and no provider needed — it works with no key configured, no network, and no tokens spent, which is the correct posture for a question whose answer d47 already holds. Separately the two dates go into the **game-state block**, which sits below the cache breakpoint in the prompt order (tools → guardrails → persona → About Me → *break* → history → game state), so a value that changes every turn costs nothing in cache terms and the persona can reference the date in conversation without a tool call. **A tool was the obvious answer and is the wrong one**: the advertised surface is paid for on every turn whether or not anybody asks the time. **Both dates are supplied pre-computed and the model is never asked to add 1286** — that is arithmetic, and a model doing arithmetic in prose is wrong occasionally and confidently, which is the failure mode this repository is written against. **Cancelling a timer or an alarm is the Commander's, and reachable from the panel and the keyword router only.** Protected is a property of the caller rather than the modality, so a spoken cancel still works while a hostile in-game message cannot reach one — and an alarm somebody relies on to leave the house is worth that line being drawn before anybody asks for it.

- [x] **Phase 25 — The panel becomes a place**
  - [x] One transcript, three views - Conversation, Technical and the log file collapse into a single **Transcript** tab with three modes, because they are three readings of one thing rather than three destinations. That frees the bar for the surfaces below without it growing: **Transcript, Checklist, Loadout, Engineers, Utilities, Settings** — six, and five in the headset, where Settings stays hidden for the reason `PanelView.axaml` already records, that a 1180-pixel nav column at a metre is a wall rather than a settings surface. The mode control is **not a second tab strip** under the first; two stacked strips read worse than the eight flat tabs this avoids. One asymmetry to keep rather than smooth over: Conversation and Technical are the same exchange at two verbosities, and the log is **a file read off disk**, which is why it carries the busy glyph and why the collapse is three modes rather than a single toggle.
  - [x] Drill in, and find your way back - Every new surface is a stack — Fleet → Ship → Slot → Blueprint — and **the tab is the root rather than the first level**, so pressing an already-selected tab returns to it. That costs something to build: the tabs are `RadioButton`s and re-pressing a checked one announces nothing, so the behaviour has to be added rather than inherited. **The breadcrumb is both the back affordance and the you-are-here**, because a headset has no title bar to orient by and losing your place is expensive when you cannot glance at a second monitor. Back is three routes that must agree — the breadcrumb, a controller button, and a phrase — and each crumb is a word that can be said as well as pressed. **Voice jumps levels**, so the stack has to materialise mid-drill with a valid trail behind it rather than only being built by walking. Drill state survives a tab switch, and a tab with more than one root keeps a stack per root.
  - [x] The panel resizes and zooms - The big panel becomes resizable as well as zoomable, and the two levers are different things worth keeping distinct in the Commander's head: **pixels decide how much the image can hold, metres decide how big it looks in the room, and zoom decides how much logical layout those pixels carry.** Zoom is already a `LayoutTransform`, so it re-measures and rewraps rather than merely scaling — which makes it a **density** control, not just a legibility one. On `ZoomLadder`'s Chrome-derived rungs the default 1024x640 panel presents 1365x853 logical at 75% and 512x320 at 200%, so a Commander who wants a whole ship's slots visible zooms out and one who wants to read across the cockpit zooms in. **That trade is theirs, and the layout's job is to survive all of it.** Which makes the requirement responsive rather than fixed: **one design across roughly a 4x range of logical space**, reflowing between one, two and three panes. Resizing pixels has a ceiling that is not code — past what the quad subtends on the headset panel, extra pixels are render cost with nothing to show for it — and cost is linear in them, which `VrPanelSurface` already says. **VR leads throughout and this is not a preference**: `VrPanelSurface` states that the windowed panel cannot be more functional than the headset one by construction, so the desktop breathes more and never does more.
  - [x] Choosing takes the panel - A chooser **replaces the panel until it is dismissed**, which makes it a level of the stack rather than a popup. Popups cannot exist in the VR path at all: `IsDropDownOpen = true` exits at `0xC00000FD` before any dispatcher work with no exception and nothing in the log, because the panel's window is never shown and a popup has no top level to hang from — and forcing it into the window's own overlay layer is the same crash. **A second overlay quad was the obvious alternative and is not the answer.** `SteamVrRuntime` already serves a list of surfaces and already places one — the cursor — in world space from a ray intersection, so the machinery exists; but the crash is Avalonia's rather than OpenVR's, so a new quad still needs a second never-shown window and its own render target, plus a ray priority rule between overlapping quads, and the result would be a VR-only mechanism for a control the desktop also has. Taking the panel needs none of that, is in the widget tree so both surfaces get it identically, and **fixes ergonomics rather than only occlusion** — a full panel is roughly sixteen rows at a ray-safe height and twenty-five zoomed out, where a layer over the page is fewer. **The chooser carries what it is choosing for in its header** — the slot, its size, and what is fitted now — which a dropdown cannot do and is the one thing the takeover would otherwise cost. Drawn as a level and **behaving as a modal**: no navigating away mid-choice, with identical affordances so it never reads as a special case. **Page or layer is declared per call site, never computed from list length** — a module picker is a page, a five-item settings enum stays the in-tree layer — because a control that behaves differently on different days is a control nobody trusts.
  - [x] Say it, or type it - Text entry is **voice first with the drawn keyboard as the fallback**, and which surface opens is declared per call site: a system name is far easier said than typed and a number is the reverse. **The correction loop is the same one the timers use** — d47 shows and says what it heard, and the Commander confirms or corrects — which also satisfies the rule `69fbd3e` already set, that what is entered reaches the box **once, on Done**, because a system name arriving letter by letter is eleven wrong values on the way to the right one. A spoken value is naturally atomic and fits that better than typing does. **The keyboard returns by itself on the three failures d47 can detect**: nothing heard at all, a transcription below confidence, or a value that fails to resolve — and the third is real rather than theoretical, since the two-resolver check already catches a renamed system and an invented one. Only *confident, valid and still wrong* needs the human, and that is what the readback is for. A dismissed keyboard needs a **visible listening state** with the partial transcription showing, or the Commander is talking at a blank page. **A physical keyboard is not part of this and the reason is recorded rather than left to be rediscovered**: every route that would deliver characters while Elite holds foreground is already closed in `PushToTalkKey` — `WH_KEYBOARD_LL` is forbidden as a global input chokepoint, `RIDEV_INPUTSINK` was rejected on privacy because it delivers every keystroke on the system including passwords typed into other applications, and `GetAsyncKeyState` reads exactly one bound virtual-key code and cannot be generalised to text. The only legal route left is giving d47's own window focus, which takes Elite's keyboard away mid-session, and that is a worse trade than a drawn keyboard nobody has to use.
  - [x] The checklist leaves its window - `ChecklistWindow` becomes a tab, and **the headline is not tidiness**: a `Window` cannot appear in the headset, so a Commander in VR cannot see their checklist at all today. It needs the big area for the reason the popup never had it — the list runs to hundreds of lines. **One list in the Commander's order**, with scope shown on each line rather than carving the page into separate lists: what gets reordered on a whim is everything being worked on, not one ship's share of it, so `ChecklistScope` is a **label and a filter, never a partition**. **Reordering is not a drag** — a drag is the worst gesture available to a ray at a metre — so the selected line grows a pair of movers, and the phrase does it without aiming at all. **A state is a next action rather than a badge**, which is what `ChecklistState`'s own comment asks for: `Elsewhere` says transfer it rather than grind for it, `Blocked` says nothing can be done until a grade is reached, `Unverified` says the journal wrote `Engine_Dirty` and nothing shipped joins that name to the table so d47 will not claim it, and `Stale` says the list is about a hull that is not there any more. Colour is spent only where something is wrong. Authored lines keep their checkbox and derived ones keep none, unchanged. **Suggestions become a page rather than an interruption**: everything `ChecklistProposals` is holding waits in one place, a `Revise` arrives as a diff so an ordering the Commander spent time on survives a plan change, and accepting stays their own act — reachable from that page and a spoken yes, and from nothing else.

- [x] **Phase 26 — Ships**
  - [x] A plan is keyed to its slot - **Before anything writes a plan to disk**, because it is cheap now and expensive afterwards. Today `EngineeringPlan` builds items with `Key = ChecklistKeys.For(intent)` (`EngineeringPlan.cs:177`) and says so in as many words — *identity is the intent, so this falls out of the key rather than needing a rule of its own*. That is exactly right for items regenerated from scratch each evaluation, and it does not survive a plan the Commander edits: changing a slot from a long-range pulse laser to an overcharged multi-cannon is not a delete and an add, **it is still the third hardpoint on the same hull**. So identity is `ChecklistScope` plus the slot, which `ChecklistItemId` already expresses and which needs no counter and no tombstone bookkeeping, because a slot exists as long as the hull does. **One build per ship**: comparing a combat fit against an exploration fit for the same hull is a planner feature this deliberately does not have, and slot identity is what makes that a decision rather than an accident.
  - [x] The fleet, and the fleet you intend - The Loadout tab opens on the fleet — **a root rather than a level** — and it earns being landed on by answering where each ship is and how its plans stand before anything is drilled. **A hull you do not own is not in the fleet.** It is a separate class with no `ShipID`, since `ChecklistScope.Ship(int)` takes the journal's id and a Corsair nobody has bought has none, and **acquiring the hull is the plan's first step** rather than a precondition sitting outside it. Owned is derived and not editable; intended is authored and is — the same rule the checklist already draws between a line the journal settles and a line a person does, so it should look like the same rule. **Buying one adopts the plan rather than making the Commander re-point it**: `ShipyardBuy` names the hull and the new id, d47 matches on hull and proposes through `ChecklistProposals`, and the Commander accepts. Which is the third use of that mechanism and a good sign the trust boundary sits in the right place. It also means a prospective plan's identity has to be stable and independent of `ShipID` from the moment it is created, or there is nothing to rebind.
  - [x] What is fitted and what you want - Fleet → Ship → Slot, with the slot list an **index rather than a table**: one line each, a mark where a plan exists, and everything else in the pane that opens. That is what lets one layout survive from 512 to 2048 logical pixels. **Fitted and planned are two blocks and never one merged line**, because a plan is a second thing the Commander wants rather than an edit to the truth. **A plan carries the journal's verdict with its date and no checkbox** — `ChecklistEvaluator` already answers null for *nothing can be said right now*, which is what a ship you are not flying looks like, and the stored verdict then stands as of when it was taken rather than resetting to open on the absence of evidence. So the page says *not fitted, as of three days ago* rather than showing a blank that implies disagreement. Cost is per plan and on the slot: `PlanIngredient` already carries held, needed and short, and `EngineeringRules.RollsFor` already turns a grade and an engineer's rank into a roll count, so a grade 5 blueprint at a grade 5 engineer is five applications of the recipe and the arithmetic is done rather than estimated. **The ray points and the voice edits**, so the page optimises for being read rather than for manipulation density — one utterance does what six ray presses would, and the say-line along the bottom is how a Commander learns the phrase for what they are looking at.
  - [x] A plan reaches the checklist when you say so - **The plan owns what and the checklist owns when.** Ships keeps its own store and nothing crosses into the checklist unasked; promotion goes through `ChecklistProposals` and accepting stays the Commander's act. The link is a **reference rather than a snapshot**, so a checklist line follows the plan it came from while the Commander reorders freely — which is the whole reason the slot key above has to be stable. **Promotion is one-to-many**: `EngineeringPlan` already emits an `EngineerAccess` step beside a modification, so one planned change produces the modification plus whatever unlocking and ranking it needs, and each of those lines points back at the plan item that caused it. Deleting a plan therefore has to clean its whole subtree rather than one line. A promoted line whose plan is deleted is **kept rather than vanished**, the way completed items already sit below the line with their count showing — because the Commander ordered their list around it and silently removing it is a history that lies.

- [x] **Phase 27 — Suits and weapons, and the gap**
  - [x] The same page, on foot - Suits and weapons is the Ships page instantiated against `OnFootPlan`, which Core already models in parallel with `EngineeringPlan` — so this is one page kind built once and shown twice, in the same spirit as one widget tree rendering to two surfaces. It stays a **second mode rather than a second tab**, because the game separates ship and on-foot hard and so does its vocabulary, but nothing about the layout is redrawn. `ChecklistScope` already has `Suit` and `Weapon`, keyed on `SuitID` — which survives a grade change where the symbol does not — and `SuitModuleID`, so the scoping this needs is built. What differs is the shape of the thing being planned: a suit takes grades and mods rather than modules in slots, so **slot identity has to be read as the mod slot it is** rather than assumed to look like a hardpoint. **Built, and the mod slot had to be invented rather than read**: Elite reports what is fitted as a *set* with no positions in it, so the slots are `Grade` then `Mod 1` to `Mod 4`, they are d47's own, and the page says so where a Commander could otherwise read the third one as the game's third. One correction to the plan of record on the way past — **on foot the buy event carries the id**, which is the exact opposite of the ship side: `BuySuit` carries `SuitID` and `BuyWeapon` carries `SuitModuleID`, so adoption is one event where Phase 26 needed the second of two.
  - [x] Gap analysis - A third root-only mode reading across both the others, because a Commander gathering materials does not care which ship wanted them. **Not called a wishlist**: a wishlist is a list of things you want, which is what the plans are — this is the arithmetic between what they need and what you are carrying. **The ledgers are never totalled together.** Raw, manufactured, encoded and the on-foot holds are separate with separate caps and no exchange between them, which is exactly why `PlanIngredient` keeps `Capacity` per ledger and says the ledgers must not be summed; a single headline number over the top of them would be a lie. The one figure that spans everything counts units still to find, which is a shopping list rather than a balance. **A shortfall reads back to what wants it** — the ships and slots that asked — which is what makes the roll-up navigable instead of merely a total. **Material trading is included and stays secondary**: `EngineeringRules.TradeRate` already knows what a trader charges and `Materials.tsv` already carries the `line` column that is *the trader's grid column, never the journal's category*, which is the distinction that makes the maths correct — so the headline stays the honest raw shortfall and trade appears as a second line beside it. Whether unowned hulls count is **a filter rather than a decision taken once on the Commander's behalf**, because counting them is honest about the whole ambition and excluding them answers what can be finished now, and both are real questions. **Built, and it is costed one slot at a time and merged afterwards** — the totals are identical either way, and it is the only arrangement in which a shortfall can name the ships and slots that asked for it. The advertised tool surface went *down*, from 39,693 bytes to 39,639: everything this phase adds to the model-facing side is Protected, and `plan_on_foot_build` now writes the plan rather than proposing straight to the checklist.

The summary carries the count that belongs to the other tab — **how many of your plans are waiting on somebody you have not met**. One pane rather than two, since an engineer row already holds name, specialities, location and status and a second column would only repeat them.
  - [ ] The fastest way in - **A solver rather than a display, and it has to show its work.** Walking one engineer's referral chain is exact and cheap — `referred_by` is a single parent, so Broo Tarquin ← Hera Tani ← Liz Ryder is unambiguous — but it answers the wrong question. The real one is *how do I get everything my plans need*, and two things make that harder than a walk: a blueprint usually lists several engineers, and one unlock covers many plans — Marsha Hicks rolls multi-cannons, cannons, fragment cannons, fuel scoops, refineries and four limpet controllers, all at grade 5. So the best next unlock is the one that satisfies the most of what is planned, not the shortest chain. **Ranked by fastest unlock and distance together, expressed in one unit rather than balanced by a tuning constant**: distance converts to jumps using the jump range of the ship actually being flown, which d47 knows from the loadout, and each unmet step carries its own trip cost — a tribute of fifty units is one shopping run to a known system, and a combat rank is not a trip at all and should be weighed as the open-ended thing it is instead of being pretended into a number. **Colonia then needs no rule of its own**: 22,000 ly is hundreds of jumps and swamps any step count, and because distance is measured from where the Commander is, being in Colonia flips it automatically. **The ranking is explained on the page** — one step, 84 ly, about three jumps, and four other planned things covered — because a ranking nobody can inspect is an oracle, and when it is wrong, or when the Commander would rather go elsewhere anyway, they cannot tell a bad answer from a bug. The route promotes to the checklist as a chain rather than a line, which is what `EngineeringPlan` already does when it emits an access step beside a modification.

- [ ] **Phase 29 — Bring your own model**
  - [ ] A turn answered by OpenAI - The second `ILlmProvider`, over the **Responses API**, streamed so speech still starts at the first sentence boundary. Much of this is already specified rather than newly decided: `architecture.md` §6 has said from the start that two implementations ship and that an OpenAI-protocol endpoint is *"a first-class peer rather than a port"*, `ILlmProvider.Id` is documented as `"anthropic", "openai"`, and the endpoint, model and key rows are generated from the catalog, so the settings surface costs nothing. **Responses rather than Chat Completions, and the reason is web search rather than novelty.** Server-side search is now a named entry in the tools array everywhere it exists, and the address decides whether it can be reached: OpenAI's `web_search` and xAI's `x_search` are Responses tools, and xAI deprecated the older `search_parameters` on Chat Completions on 2026-01-12. So a Commander who switches provider keeps the capability instead of watching it go dark, which is worth a second decoder on its own. The entry **accepts a custom endpoint**, because xAI and OpenRouter both take the OpenAI shape at their own address — reaching Grok is a base URL and a model name, not a third implementation. Hand-rolled HTTP and SSE rather than the official SDK, which is MIT and would pass the licence gate: the Edge and ElevenLabs voices are the precedent, and a strongly-typed client is exactly where tolerance for a server that deviates goes to die.
  - [ ] A turn answered by a machine you own - The same seam over **Chat Completions**, against Ollama, LM Studio, vLLM or llama.cpp. **A separate catalog entry rather than the first one pointed elsewhere**, because `Egress` is one string per provider and no single string can say both *everything goes to OpenAI* and *nothing leaves this machine*; it also splits the secret, which is correct, since an OpenRouter key is not an OpenAI key. **The key becomes optional, and that is a change rather than a setting.** `NeedsKey` is derived from whether a secret name exists (`LlmProviderCatalog.cs:51`) and `ApplyLlmSettings` only builds a provider inside `if (ResolveKey(selected) is { } resolved)` (`AppHost.cs:1422`), so a local server with no account is unreachable by construction rather than by decision — and the same assumption sits in `FirstRun.IsNeeded` and in the disclosure's `usable` test. No server-side search exists on this path and it says so, in the wording that already covers an endpoint offering none. **Two construction sites become one factory**: `AppHost.cs:1424` and `AppHost.cs:3376` both switch on the provider id and both end `_ => null` with the same sentence, and a third provider makes them drift.
  - [ ] What the endpoint can actually do - A handshake when the endpoint changes rather than a guess. `GET /v1/models` confirms the thing speaks the protocol at all and **fills the model picker, which is empty for a custom endpoint today by deliberate design** — `ModelsFor` returns nothing for an address it does not know, on the correct grounds that a model id belongs to its endpoint's namespace and offering `claude-opus-5` to somebody else's gateway is a stale selection waiting to fail. That decision stands; what changes is that the endpoint can now be asked, so the list becomes the endpoint's own rather than this provider's or nothing. **What a model list cannot answer is learned from the first failure, not assumed**: whether tool calls work, whether reasoning effort is accepted, whether usage comes back at all. The rule is advertise, then demote — a rejection names the field it rejected, so the capability turns off for that endpoint for the session and the turn retries once without it. **Once per capability per endpoint, never a loop**, because a retry policy that searches for a working request shape is indistinguishable from an outage. `LlmProviderCapabilities` already has every flag this needs and already treats absence as a capability that is off rather than a failure to handle.
  - [ ] A turn priced on the right arithmetic - **Three things in the pricing path are Anthropic's numbers wearing no label, and each is wrong quietly rather than loudly.** `LlmUsage.TotalInputTokens` sums input, cache writes and cache reads because Anthropic's `input_tokens` **excludes** the cached part — OpenAI's `prompt_tokens` **includes** it, so the same sum double-counts every cached turn unless the seam normalises. `ModelPrice` derives its cache rates rather than listing them, at 1.25x input to write and 0.1x to read, which are Anthropic's terms; OpenAI charges nothing to write and discounts reads by a different factor, so every OpenAI turn is mispriced upward until those become per-row values with the current pair as the default. And `SpendTracker.UnexplainedColdPrefixes` counts turns that *write* cache with no sanctioned cause, which is a detector that cannot fire on a provider that never reports a write — it would read as caching being perfect rather than as the instrument not working here, and the analogue is the inverse signal, a turn reporting no cache read when the prefix did not change. **A fourth is not arithmetic but a default**: streamed Chat Completions returns no usage at all unless it is asked for, and a missing usage block priced as zero reports a paid session as free, which is strictly worse than the unpriced path that already exists for a model with no table entry. An unknown model stays unpriced. **A loopback endpoint is priced at zero and says why**, because "unknown" repeated forever about a model that genuinely costs nothing is noise pretending to be rigour.
  - [ ] Say where it actually went - The disclosure destination **computed from the endpoint rather than fixed per provider**. A Commander pointed at `127.0.0.1` should read that nothing leaves this machine, and one pointed at a gateway should read its address — and this is the first time the honest answer to *what is leaving* is *nothing*, which Phase 4's amendment made a matter of the enumeration being truthful rather than of a local-only mode being promised. **The trust boundary widens here and needs no new machinery, which is worth stating rather than leaving to be noticed.** The attacker set gains whoever runs the endpoint, and a hostile gateway can drive tool calls directly rather than having to talk a model into it. That is survivable only because the protected set is unreachable from the tool surface entirely and protection is a property of the caller rather than of the modality — the invariant was written for a hostile in-game message and it is what makes pointing d47 at a stranger's address a decision rather than a hole.
